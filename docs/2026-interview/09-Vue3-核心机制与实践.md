# Vue 3 核心机制与实践

> 学 Vue 3 不要先背所有 API。先理解它把 Vue 2 中分散在 `data`、`computed`、`watch`、`methods` 的同一类业务逻辑放到一起组织。

## 知识链

从响应式状态开始，经过派生值与副作用、组件输入输出、逻辑复用，再进入内置组件、渲染性能和 SSR。Vue 3 的 API 很多，但面试主线始终是：状态由谁拥有、什么时候更新、组件如何通信、资源如何清理。

## P0：`ref` 和 `reactive` 怎么选？

### 30 秒回答

`ref` 可以包装任意值，尤其适合基本类型、可能整体替换的值；在脚本中通过 `.value` 读写，模板会自动解包。`reactive` 只接收对象类型，返回 Proxy，适合一组相关字段。两者没有绝对高下，选择依据是状态形态和可读性，而不是为了统一一种写法。

### 展开说明

Vue 3 的响应式基于 Proxy，但 `ref` 仍然有价值：基本类型没有可代理的对象容器；整体替换对象时 `ref` 的赋值也很直观。不要把 reactive 对象直接解构为普通变量，否则会失去与源对象的响应式连接。

```ts
import { reactive, ref, toRefs } from 'vue'

const page = ref(1)
const query = reactive({ keyword: '', status: 'all' })

page.value += 1
query.keyword = 'Vue 3'

// 需要解构并在模板或其他函数中保持响应式时使用 toRefs
const { keyword, status } = toRefs(query)
```

### Vue 2 对照

Vue 2 的 `data` 会统一转成响应式对象；Vue 3 让你在 `setup` 中更显式地表达状态。不要因为 Vue 3 能自由组合，就把所有状态塞进一个大对象或大量零散 ref 中。

### 项目表达

页面搜索条件可以用一个 `reactive` 对象，因为字段属于同一表单；分页页码、加载状态、当前请求控制器更适合独立 `ref`。清楚的状态边界比 API 选择更重要。

### 可能追问

- `ref` 内部对象会响应式吗？会，Vue 会把对象值转换为响应式代理；如需保持原始对象可使用 `shallowRef` 等浅层 API。
- `reactive` 为什么不能直接替换？变量本身仍指向原 Proxy；用新对象重新赋值不会改变所有旧引用，整体替换时更适合 `ref`。

## P0：`computed`、`watch` 和 `watchEffect` 如何区别？

### 30 秒回答

`computed` 用于从响应式状态派生新值，并按依赖缓存；`watch` 用于观察明确来源，在变化后执行副作用，可取得新旧值并控制触发时机；`watchEffect` 会立即执行并自动收集同步访问到的依赖，适合简单的响应式副作用。请求、订阅和定时器等副作用都需要处理失效或清理。

### 展开说明

不要用 `watch` 去维护本可以由 `computed` 推导的状态，否则会增加同步风险。异步回调中 `watchEffect` 在第一个 `await` 之后访问的依赖不会被自动追踪，复杂场景更适合显式 `watch`。

```ts
import { computed, ref, watch } from 'vue'

const keyword = ref('')
const page = ref(1)
const requestId = ref(0)

const hasKeyword = computed(() => keyword.value.trim().length > 0)

watch([keyword, page], async ([nextKeyword, nextPage], _previous, onCleanup) => {
  const controller = new AbortController()
  const currentId = ++requestId.value

  onCleanup(() => controller.abort())

  const response = await fetch(`/api/list?q=${nextKeyword}&page=${nextPage}`, {
    signal: controller.signal,
  })
  const data = await response.json()

  if (currentId === requestId.value) {
    console.log(data)
  }
})
```

### 项目表达

搜索条件变化时我会让 `watch` 负责请求副作用，并用 cleanup 取消旧请求；展示文案、禁用状态、过滤结果等纯派生值交给 `computed`。这能避免“两个状态互相 watch 再同步”的循环。

### 可能追问

- `watch` 默认什么时候执行？默认在组件更新前的调度阶段；可通过 `flush` 调整。需要读取更新后的 DOM 时通常考虑 `flush: 'post'` 或 `nextTick`。
- 深度监听有成本吗？有。应尽量监听精确来源或使用不可变更新，而不是对大型对象无差别 `deep: true`。

## P0：Vue 3 生命周期和 Vue 2 如何对应？什么时候该清理副作用？

### 30 秒回答

Vue 3 的 `onMounted/onUpdated/onUnmounted` 对应 Vue 2 的 `mounted/updated/destroyed` 等生命周期；`setup` 本身发生在组件创建早期，没有 `this`。生命周期钩子用于与 DOM、第三方实例、订阅和定时器等外部系统同步，组件卸载时必须清理自己创建的副作用。

```ts
import { onMounted, onUnmounted, ref } from 'vue'

const width = ref(window.innerWidth)

function updateWidth() {
  width.value = window.innerWidth
}

onMounted(() => window.addEventListener('resize', updateWidth))
onUnmounted(() => window.removeEventListener('resize', updateWidth))
```

### Vue 2 对照

Vue 2 中同样需要在 `beforeDestroy/destroyed` 清理监听。Vue 3 改变的是写法，不改变“谁创建谁清理”的责任。

### 可能追问

- `onUpdated` 能随意改状态吗？不应无条件修改，否则可能触发更新循环；优先在事件、watch 或明确的副作用中更新状态。
- 组件错误怎么处理？可用 `onErrorCaptured` 在祖先组件捕获子树错误，配合全局错误处理和监控；不能把错误边界当作正常业务流程。

## P0：`<script setup>`、Props 和 Emits 如何写得清晰？

### 30 秒回答

`<script setup>` 是 Composition API 的编译期语法糖，顶层变量可直接在模板使用，减少组件选项样板。组件边界通过 `defineProps` 和 `defineEmits` 明确声明；TypeScript 下应同时把输入和事件参数类型写清楚，避免父子组件依赖隐式约定。

### 最小组件示例

```vue
<script setup lang="ts">
import { computed, ref } from 'vue'

type User = {
  id: string
  name: string
}

const props = defineProps<{
  user: User
  disabled?: boolean
}>()

const emit = defineEmits<{
  select: [id: string]
}>()

const selected = ref(false)
const buttonText = computed(() => (selected.value ? '已选择' : `选择 ${props.user.name}`))

function handleSelect() {
  if (props.disabled) return
  selected.value = true
  emit('select', props.user.id)
}
</script>

<template>
  <button :disabled="disabled" @click="handleSelect">{{ buttonText }}</button>
</template>
```

### 展开说明

Props 是单向数据流，子组件不应直接修改。需要双向绑定时可使用明确的 `v-model` 约定，或以事件把意图返回给父组件。事件名和参数类型属于组件 API，应像接口一样稳定维护。

### Vue 2 对照

Vue 2 使用 `props`、`data`、`methods`、`this.$emit` 等选项；Vue 3 `<script setup>` 把它们放到同一作用域。思路仍是单向数据流与清晰边界，变化主要在组织方式和类型能力。

### 可能追问

- `defineProps` 为什么不用 import？它是编译器宏，不是运行时普通函数。
- 组件需要暴露方法怎么办？优先通过 props/events 设计声明式 API；确实需要命令式调用时使用 template ref 和 `defineExpose`，并限制暴露面。

## P0：Vue 3 中如何实现组件双向绑定和多组 `v-model`？

### 30 秒回答

组件的 `v-model` 本质是 prop 加更新事件。默认使用 `modelValue` 和 `update:modelValue`；命名 `v-model:visible` 则对应 `visible` 与 `update:visible`。它让父组件保有状态，子组件只表达更新意图，比子组件直接改 prop 更清晰。

```vue
<script setup lang="ts">
const props = defineProps<{ visible: boolean }>()
const emit = defineEmits<{ 'update:visible': [value: boolean] }>()

function close() {
  emit('update:visible', false)
}
</script>
```

### 可能追问

- 子组件需要内部草稿怎么办？复制 prop 到本地 ref，在确认时 emit；要明确外部 prop 更新时草稿如何同步，不能悄悄双向修改。

## P0：`toRef`、`toRefs`、`shallowRef`、`markRaw` 如何选择？

### 30 秒回答

`toRef/toRefs` 用于把 reactive 对象属性保持为 ref，避免解构丢失响应式；`shallowRef` 只追踪 `.value` 整体替换，适合大型不可变数据或第三方实例；`markRaw` 标记对象不参与代理，适合不应被 Vue 代理的类实例。它们都是性能和边界工具，先确认普通 `ref/reactive` 是否真的有问题。

```ts
import { markRaw, shallowRef } from 'vue'

const chart = shallowRef<ChartInstance | null>(null)

function mountChart(instance: ChartInstance) {
  chart.value = markRaw(instance)
}
```

### 项目表达

图表、地图等第三方对象实例不应被深度代理；我会用 shallowRef 或 markRaw 保存实例，并在卸载时调用其销毁 API。

## P0：`attrs`、slot、provide/inject 怎样决定组件边界？

### 30 秒回答

Props/Emits 是组件的显式业务 API；未声明的 attribute 可通过 `$attrs` 透传给基础元素或内部组件；slot 让父组件提供结构；provide/inject 适合跨多层的稳定上下文，例如表单或主题。它们各有用途，不能用 inject 或 attrs 绕过本该声明的组件契约。

```vue
<!-- BaseButton.vue -->
<template>
  <button v-bind="$attrs"><slot /></button>
</template>
```

### 可能追问

- `$attrs` 为什么不直接叫 props？它不包含已声明的 props 和 emits，通常用于通用基础组件透传。
- inject 的风险？依赖来源不直观，注入键冲突或默认值设计不当时难调试；公共组件应提供清晰的注入约定。

## P0：什么是 composable？怎样避免把逻辑抽得更乱？

### 30 秒回答

Composable 是复用 Composition API 状态逻辑的函数，通常以 `use` 开头。它应围绕一个明确关注点提供输入、状态、操作和清理，例如分页请求、权限判断或窗口尺寸。抽取前先确定边界；如果函数同时处理请求、弹窗、表单、路由和埋点，通常仍然过大。

### 展开说明

Composable 不是 Vuex 替代品。它更适合组件或页面级逻辑复用；跨路由、跨模块、需要长期共享的状态仍要评估 Pinia 或服务端缓存策略。

```ts
import { onUnmounted, ref } from 'vue'

export function useInterval(callback: () => void, delay = 5_000) {
  const active = ref(false)
  let timer: number | undefined

  function start() {
    if (timer !== undefined) return
    timer = window.setInterval(callback, delay)
    active.value = true
  }

  function stop() {
    if (timer === undefined) return
    window.clearInterval(timer)
    timer = undefined
    active.value = false
  }

  onUnmounted(stop)
  return { active, start, stop }
}
```

### 项目表达

我会将请求列表、分页、取消、加载状态等组合成可测试的 composable；页面只负责传入筛选条件与组织 UI。若某些状态需要跨页面共享，再把它提升到 Store，不会一开始全局化。

### 可能追问

- Composable 内部状态每次调用共享吗？普通 composable 每次调用各自创建状态；把状态定义在函数外才会变成共享单例，需要有意识地使用。
- 为什么要在 composable 中清理？它可能注册监听、定时器或请求，生命周期结束时需要停止副作用。

## P1：动态组件与 KeepAlive 在 Vue 3 中如何使用？

### 30 秒回答

`<component :is="...">` 用于在同一位置切换不同组件；`<KeepAlive>` 缓存被切换走的组件实例，并触发 `onActivated/onDeactivated`。它适合多标签页、列表详情往返等需要保留局部状态的场景，但必须控制 include/exclude、缓存上限和数据失效策略。

```vue
<KeepAlive :max="10">
  <component :is="currentView" />
</KeepAlive>
```

### 项目表达

缓存页面回到前台时，我会在 `onActivated` 判断数据是否失效，而不是只因为组件没有销毁就假定数据一直可靠。

## P1：Teleport、Transition 和指令分别解决什么问题？

### 30 秒回答

Teleport 解决视觉 DOM 层级问题，例如弹窗挂到 `body` 避开裁剪与层叠上下文；Transition 协调条件渲染或列表变化的过渡类名；自定义指令适合直接操作 DOM 的可复用行为，例如自动聚焦。优先使用组件和响应式数据，只有 DOM 行为本身才用指令。

```ts
const vFocus = {
  mounted(element: HTMLInputElement) {
    element.focus()
  },
}
```

## P1：异步组件和 Suspense 应如何取舍？

### 30 秒回答

异步组件通过 `defineAsyncComponent` 延迟加载低频或体积大的组件；Suspense 可以协调其异步依赖和 fallback。它们适合改善资源加载体验，但页面的数据 loading/error 状态仍需有明确业务设计，不能把所有请求逻辑塞进 Suspense。

### 可能追问

- 异步组件加载失败怎么办？配置错误组件、超时和重试策略，并上报资源加载错误。
- 首屏组件都应该懒加载吗？不应该。首屏关键内容延迟加载可能反而损害 LCP。

## P1：Vue 3 的模板 ref、`defineExpose` 和命令式调用如何控制？

### 30 秒回答

template ref 用于在挂载后访问 DOM 或子组件公开能力。子组件使用 `<script setup>` 时默认是封闭的，需要 `defineExpose` 明确暴露方法。命令式调用应是例外，例如表单校验或焦点控制；业务数据流仍优先用 props 和 emits。

```vue
<!-- Child.vue -->
<script setup lang="ts">
function validate() {
  return true
}
defineExpose({ validate })
</script>
```

## P1：Vue 3 渲染性能有哪些常见优化点？

### 30 秒回答

先观察组件更新原因，再减少不必要工作：保持 props 稳定、避免在模板里创建昂贵表达式、拆分长列表并虚拟化、对大对象选择合适的响应式深度、按路由或组件分包。`v-once`、`v-memo` 是针对明确稳定子树的优化工具，滥用会降低可维护性并导致界面不更新。

### 项目表达

我会先用 Vue Devtools 的组件更新信息和浏览器 Performance 找到具体更新源，再优化；不会只因“组件很多”就机械拆分或缓存。

## P2：SSR 与 hydration 的关键风险是什么？

### 30 秒回答

SSR 先在服务端生成 HTML，有利于首屏和 SEO；客户端再 hydration，把事件和响应式能力附着到已有 DOM。服务端和客户端首次渲染必须一致，随机数、时间、浏览器专属 API、登录态差异都可能造成 hydration mismatch。是否采用 SSR 要看 SEO、首屏、服务端成本和复杂度。
