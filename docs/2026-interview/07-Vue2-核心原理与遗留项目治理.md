# Vue 2 核心原理与遗留项目治理

> Vue 2 经验不是需要回避的“旧技术”，关键在于能说明它的边界，并展示你如何把稳定的存量系统维护好。

## 知识链

先从响应式、更新调度和生命周期理解“数据如何变成 DOM”，再串到组件通信、虚拟 DOM、路由和状态管理。这样遇到“页面为什么没更新”“组件切换为什么丢状态”“权限路由如何恢复”时，能从机制讲到工程处理。

## P0：Vue 2 的响应式原理和边界是什么？

### 30 秒回答

Vue 2 在初始化时通过 `Object.defineProperty` 把已有对象属性转换为 getter/setter。渲染或计算过程中读取属性会收集依赖，属性写入时通知相关 watcher 更新。它无法天然拦截对象新增或删除属性，也无法直接拦截数组索引赋值和长度修改；Vue 2 通过改写部分数组变更方法处理常见场景，新增对象属性需要 `Vue.set` 或 `this.$set`。

### 展开说明

这套机制说明了为什么 Vue 2 对数据初始化有要求，也解释了为什么数组和动态字段是常见坑。不要把 Vue 2 的限制说成“数组完全不能响应”，它可以响应 `push`、`splice` 等被拦截的方法；问题在于索引赋值和长度修改等操作。

```js
// Vue 2：以下写法不会被可靠地侦测到
this.items[1] = nextItem
this.items.length = 0
this.form.extraField = 'value'

// 使用受 Vue 2 支持的更新方式
this.$set(this.items, 1, nextItem)
this.items.splice(0)
this.$set(this.form, 'extraField', 'value')
```

### 项目表达

维护 Vue 2 表单时，我会在初始化阶段定义完整的数据结构，动态字段则通过 `$set` 或不可变替换处理。排查“数据变了页面没变”时，先确认是否踩到了新增属性、数组索引或组件 prop 修改等边界。

### 可能追问

- Vue 3 为什么改善了这些问题？Vue 3 用 Proxy 代理对象访问和修改，可拦截新增、删除、数组索引与长度等操作；它也有自己的边界，例如只能代理对象，解构响应式对象时仍可能丢失响应式连接。
- `Object.defineProperty` 可以 polyfill Proxy 吗？不能。Proxy 能拦截的对象级操作范围更广，不能靠普通 polyfill 完整模拟。

## P0：组件的 `data` 为什么必须是函数？根实例为什么例外？

### 30 秒回答

组件可能被复用出多个实例，`data` 写成函数可以为每个实例返回一份独立状态，避免一个实例修改数据污染另一个。根实例通常只创建一次，因此可以使用对象；但在统一代码风格下写成函数也没有问题。

```js
export default {
  data() {
    return {
      page: 1,
      form: { keyword: '' },
    }
  },
}
```

### 可能追问

- `props` 的默认对象或数组为什么也用工厂函数？同样是避免多个实例共享可变引用。

## P0：`computed` 和 `watch` 如何选择？

### 30 秒回答

`computed` 用于由已有状态推导出的新值，按依赖缓存且应保持无副作用；`watch` 用于状态变化后执行副作用，例如请求、日志、同步外部系统。不要用 watch 维护本可由 computed 得出的字段，否则会制造同步时序和循环问题。

```js
computed: {
  fullName() {
    return `${this.firstName} ${this.lastName}`
  },
},
watch: {
  keyword: {
    handler(value) {
      this.loadList(value)
    },
    immediate: true,
  },
},
```

### 可能追问

- `deep: true` 能监听嵌套变化吗？能，但旧值和新值在原地修改时常是同一引用，且遍历大对象有成本；应优先缩小监听范围。
- computed 可以有 setter 吗？可以，适合明确的双向映射，但不要用它隐藏复杂副作用。

## P0：Vue 的异步更新和 `$nextTick` 是什么？

### 30 秒回答

Vue 会把同一轮同步代码中的多次响应式修改合并，异步刷新组件更新队列，避免每次赋值都立刻重渲染。`$nextTick` 用于在本轮状态更新对应的 DOM 刷新后执行逻辑，例如读取更新后的元素尺寸；它不是“等待任意异步请求完成”的工具。

### 展开说明

Vue 2 会根据环境选择 Promise、MutationObserver、setImmediate 或 setTimeout 等调度机制。面试中无需背源码分支，重点说明批处理目标、DOM 时机与使用边界。

```js
this.expanded = true

// 此时响应式状态已改变，但 DOM 尚未保证完成刷新
this.$nextTick(() => {
  const height = this.$refs.panel.offsetHeight
  console.log(height)
})
```

### 项目表达

只有必须读取更新后 DOM 时才使用 `$nextTick`。如果只是计算派生数据，应使用 `computed`；如果只是响应状态变化执行副作用，应考虑 `watch`。把业务流程大量包进 `$nextTick` 往往会掩盖状态设计问题。

### 可能追问

- `$nextTick` 与 `setTimeout` 一样吗？不一样。前者绑定 Vue 的更新队列并通常在更早的微任务时机执行；后者只是在未来任务中排队，不能保证对应 Vue 更新关系。
- 为什么不能立刻拿到 DOM？响应式状态改变与浏览器实际渲染不是同一步，Vue 需要合并多个变化。

## P0：Vue 2 生命周期与父子组件顺序如何理解？

### 30 秒回答

创建阶段主要完成选项初始化和首次渲染，挂载后才能安全访问已渲染 DOM，更新阶段响应数据变化，销毁阶段清理副作用。父子组件首次挂载通常是父 `beforeCreate/created`，子组件完成创建和挂载后，父组件再完成挂载；不要靠死记全部顺序替代真实的组件边界设计。

### 展开说明

`created` 中可发请求，但 DOM 尚未挂载；需要依赖真实元素尺寸或第三方 DOM 库时应在 `mounted` 或 `$nextTick` 后处理。`beforeDestroy/destroyed` 用于清理原生监听、定时器、订阅和手工创建的实例。

### 项目表达

请求放在 `created` 还是 `mounted` 取决于是否依赖 DOM。对路由切换频繁的页面，我更关心取消旧请求和清理监听，而不是机械规定“请求必须写在哪个钩子”。

## P0：Vue 2 的组件通信方式怎么选？

### 30 秒回答

父子组件优先 `props` 向下、`$emit` 向上；跨层但有明确上下文的场景用 `provide/inject`；需要命令式访问时使用 `ref`；跨页面共享状态用 Vuex。EventBus、`$parent`、`$root` 容易形成隐式依赖，存量项目可维护但新代码不应优先采用。

```vue
<!-- Child.vue -->
<script>
export default {
  props: { value: String },
  methods: {
    update(value) {
      this.$emit('input', value)
    },
  },
}
</script>
```

### 可能追问

- 为什么不能直接改 prop？所有权在父组件，直接修改会破坏单向数据流并触发 Vue 警告。
- provide/inject 是否响应式？注入的是提供者传入的引用；若要响应式更新，需要提供响应式对象或通过明确 API 更新。

## P0：`key` 在列表渲染中为什么重要？

### 30 秒回答

`key` 给虚拟节点稳定身份，Vue 在更新列表时据此复用、移动或销毁对应的真实 DOM 和组件实例。使用稳定、唯一的业务 ID 能保留正确的输入状态和组件状态；用数组下标作 key 在列表会插入、删除或排序时容易让状态错位。

### 展开说明

`key` 不是为了“让 diff 更快”的万能开关，而是为了正确性和可预测性。没有 key 时框架可复用相同位置节点，某些简单静态列表没问题，但带输入框、动画或局部状态时风险明显。

```vue
<template>
  <li v-for="user in users" :key="user.id">
    <input v-model="user.name" />
  </li>
</template>
```

### 项目表达

我会检查 key 是否真的稳定：数据库 ID、后端唯一编码通常可用；随机值和渲染时生成的时间戳会导致每次都重新创建节点。组件需要强制重建时才有意识地改变 key。

### 可能追问

- 为什么 index 有时看上去能用？数据仅追加、没有本地状态时可能暂时没有问题，但它把正确性建立在脆弱的列表顺序假设上。
- `v-if` 与 `v-for` 为什么不建议同用？可读性和优先级容易造成误解，应先用 computed 过滤或在外层条件控制。

## P1：虚拟 DOM、diff 和 template 编译要怎么讲？

### 30 秒回答

模板会被编译成 render 函数，执行后得到描述 UI 的虚拟节点树；数据变化后框架比较新旧虚拟节点，在同层节点中根据类型和 key 尽量复用、移动或创建真实 DOM。虚拟 DOM 的价值是提供声明式跨平台描述与可预测更新，不是简单地说“它一定比直接操作 DOM 快”。

### 展开说明

真实 DOM 操作的成本取决于场景，手工精确更新可能更快；框架的优势是把绝大多数复杂更新管理起来。列表 diff 的核心问题正是节点身份，因此 key 与虚拟 DOM 需要放在一起理解。

## P1：`v-if`、`v-show`、`v-html` 有什么差异和风险？

### 30 秒回答

`v-if` 控制条件块的创建与销毁，初始为 false 时不会创建；`v-show` 始终创建节点，只切换 `display`，适合频繁显隐；`v-html` 设置 `innerHTML`，只有可信或经过净化的内容才能使用，否则会带来 XSS 风险。

### 项目表达

选择 `v-if/v-show` 时看初始化成本、切换频率和组件状态是否应保留。富文本展示要有服务端或可信客户端净化策略，不能把接口返回的 HTML 直接塞进 `v-html`。

## P1：`keep-alive` 解决什么问题，如何避免缓存错误？

### 30 秒回答

`keep-alive` 会缓存动态组件或路由组件实例，切换时触发 `activated/deactivated` 而不是反复创建销毁，适合保留列表滚动位置和筛选条件。缓存不是免费资源，要通过 include/exclude、key 和失效策略控制，避免展示陈旧数据或长期占用内存。

### 可能追问

- 页面从详情返回列表时何时刷新？根据数据是否可能变化，在 `activated` 中按版本、时间或显式标记刷新，而不是每次都全量请求。

## P1：Vue Router 的 hash/history、守卫和懒加载怎样关联？

### 30 秒回答

hash 模式不依赖服务端重写，URL 带 `#`；history 模式 URL 更自然，但刷新深层路由时服务端要回退到入口 HTML。守卫用于认证、权限和必要前置判断，懒加载把路由组件拆成异步 chunk。前端守卫只改善体验，服务端才是权限最终边界。

```js
const UserPage = () => import('./views/UserPage.vue')

router.beforeEach((to, from, next) => {
  if (to.meta.requiresAuth && !store.state.token) {
    next({ name: 'login', query: { redirect: to.fullPath } })
    return
  }
  next()
})
```

## P1：mixin 有什么问题，存量项目怎么处理？

### 30 秒回答

mixin 能复用选项，但会产生命名冲突、来源不清和隐式依赖，多个 mixin 叠加后难以追踪逻辑。存量项目可逐步收敛、补文档和测试；新 Vue 3 代码优先使用 composable，以显式导入和返回值表达依赖。

## P1：Vue 2 页面性能问题如何排查？

### 30 秒回答

先定位是请求慢、长列表、重复渲染、计算属性开销、图片资源还是浏览器布局绘制问题。Vue 层面可通过稳定 key、拆分组件、虚拟列表、避免不必要的深度监听和大对象响应式化优化；仍要用浏览器 Performance 与 Vue Devtools 验证。

## P0：Vuex 在 Vue 2 项目中应该管理什么？

### 30 秒回答

Vuex 适合管理跨页面、跨组件共享且需要明确变更路径的状态，例如当前用户、权限、全局配置和需要跨路由保留的业务上下文。页面临时输入、弹窗开关和只被一个组件使用的状态应该优先留在组件或页面级逻辑里，避免把所有数据塞进全局 Store。

### 展开说明

Vuex 的单向数据流是 `state -> view -> action -> mutation -> state`。mutation 保持同步，action 放异步和业务编排，这样 DevTools 能追踪状态变化。实际项目中更重要的是模块边界、命名与清理策略。

```js
const store = new Vuex.Store({
  state: { profile: null },
  mutations: {
    setProfile(state, profile) {
      state.profile = profile
    },
  },
  actions: {
    async loadProfile({ commit }) {
      const profile = await api.getProfile()
      commit('setProfile', profile)
    },
  },
})
```

### 项目表达

排查状态混乱时，我会先区分“服务端数据缓存”“跨页面共享状态”“组件局部 UI 状态”。状态边界比使用 Vuex 还是 Pinia 更先决定可维护性。

### 可能追问

- 是否所有异步都应该写在 action？全局状态相关的异步编排适合放 action；纯组件内部逻辑不必强行绕到全局 Store。
- Vuex 可以继续用吗？可以，稳定的 Vue 2 项目没有必要为替换而替换；新 Vue 3 项目通常优先考虑 Pinia。

## P1：如何治理长期维护的 Vue 2 项目？

### 30 秒回答

先稳定关键链路，再逐步降低修改成本。做法包括依赖和安全风险盘点、抽取重复业务逻辑、补充关键流程测试、统一请求与错误处理、收敛全局状态、建立发布监控和回滚方案。不是一开始就拆全部组件或全量升级框架。

### 项目表达

我会优先选择高频改动、低耦合且收益明确的区域。每次改造都设置可验证目标，例如减少重复逻辑、缩短某页面问题定位时间、补齐一条核心链路测试，而不是只用“重构完成”作为结果。
