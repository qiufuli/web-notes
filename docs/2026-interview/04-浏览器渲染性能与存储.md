# 浏览器渲染、性能与存储

> 性能题要从用户看到的现象进入：白屏、页面卡、点击没反应、滚动跳动、数据刷新不一致。先测量问题处在哪条链路，再选择优化手段。

## 一、从 JavaScript 修改到屏幕显示

### P0：浏览器经历了什么

浏览器把文本和样式变成像素，大致经过：

```text
HTML -> DOM
CSS  -> CSSOM / 样式规则
DOM + 样式 -> 样式计算 -> Layout
Layout -> Paint -> Composite -> 屏幕
```

修改 `width` 可能改变父子和兄弟的几何关系，触发布局、绘制和合成；修改颜色通常不改变几何，主要需要重绘；`transform` 和 `opacity` 在合适条件下可能主要走合成。不要把这些说成绝对保证，实际路径受页面结构、图层和浏览器实现影响。

## 二、为什么读写交错会卡

浏览器会批量处理样式修改，但读取 `offsetWidth`、`getBoundingClientRect()` 等几何信息时必须得到最新结果，可能被迫同步计算布局：

```js
box.style.width = '300px'
const width = box.offsetWidth // 可能迫使浏览器现在完成布局
box.style.width = `${width + 20}px`
```

更好的组织是先读完，再集中写：

```js
const width = box.getBoundingClientRect().width
requestAnimationFrame(() => {
  box.style.width = `${width + 20}px`
})
```

`requestAnimationFrame` 只是把视觉更新安排在下一次绘制前，不会替你消除大计算。

## 三、Core Web Vitals 如何和排查连接

### P0：LCP、INP、CLS 不是三个孤立缩写

```text
LCP：主要内容何时呈现，常受 TTFB、关键资源和首屏同步脚本影响
INP：交互到下一次绘制的响应性，常受长任务、同步布局和复杂更新影响
CLS：非预期布局位移，常来自图片尺寸、字体切换和异步插入内容
```

```js
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) console.log('long task', entry.duration)
  }
})

observer.observe({ type: 'longtask', buffered: true })
```

这只能帮助发现长任务，不是完整的指标采集方案。Lighthouse 是实验室数据，真实体验还需要 RUM 采样、版本维度和设备网络分布。

性能优化要先形成可验证目标，例如减少 LCP 关键图片等待、降低 INP 长任务、为头像预留尺寸减少 CLS，而不是只说“减少 DOM”。

## 四、从 URL 到可交互：首屏慢应该怎么拆

### P0：浏览器打开页面经历什么

```text
URL 解析 -> DNS -> TCP/TLS -> HTTP 请求
  -> HTML 解析 / DOM
  -> CSS、脚本、图片加载
  -> 样式计算、布局、绘制
  -> JS 执行、事件绑定、可交互
```

普通 script 可能暂停 HTML 解析；`defer` 并行下载，等解析完成后按文档顺序执行；`async` 下载完就执行，多个脚本之间没有顺序保证：

```html
<script src="analytics.js" async></script>
<script src="app.js" defer></script>
```

排查“接口不慢但首屏慢”，要看 Network 瀑布、TTFB、关键资源、JS 执行、布局和图片解码分别花了多少时间。

## 五、前端存储：按数据边界选择工具

### P0：Cookie、localStorage、sessionStorage、IndexedDB 怎么选

| 工具 | 适合 | 关键边界 |
| --- | --- | --- |
| Cookie | 服务端需要随请求携带的小状态 | 体积小，有请求头开销；配置 HttpOnly/Secure/SameSite |
| localStorage | 少量、长期、非敏感字符串 | 同步 API，读写大量数据会阻塞主线程 |
| sessionStorage | 当前标签页会话数据 | 生命周期短，标签页隔离 |
| IndexedDB | 较大、结构化、异步客户端数据 | 需要版本迁移、容量与一致性策略 |

```js
const preferences = { theme: 'dark', updatedAt: Date.now() }
localStorage.setItem('preferences', JSON.stringify(preferences))

const saved = JSON.parse(localStorage.getItem('preferences') ?? 'null')
```

登录态和 UI 偏好要分开设计。HttpOnly Cookie 能降低脚本直接读取令牌的风险，但仍需 CSRF 防护；任何能被脚本读取的存储都不能假设能抵御 XSS。

## 六、缓存和 Service Worker 怎样避免数据失控

HTTP 强缓存、协商缓存由浏览器网络层处理；Service Worker 可以在更前面拦截请求，自定义缓存优先级和离线回退：

```js
self.addEventListener('fetch', (event) => {
  if (event.request.destination === 'image') {
    event.respondWith(
      caches.match(event.request).then((cached) => cached || fetch(event.request)),
    )
  }
})
```

Service Worker 能力更强，也更需要版本和失效策略。缓存必须回答：数据多久过期、如何更新、旧版本如何清理、离线时展示什么，而不是简单永久缓存。

## 七、内存增长和布局偏移怎样定位

### P1：页面反复进入退出后越来越占内存

先稳定复现，观察 JS heap、DOM 节点和监听器，再用 Heap Snapshot 看引用链。重点检查定时器、全局缓存、原生监听、第三方实例和 Detached DOM：

```js
function createPolling(callback) {
  const timer = window.setInterval(callback, 5000)
  return () => window.clearInterval(timer)
}

const stopPolling = createPolling(loadData)
// 组件卸载时调用 stopPolling()
```

只有强制 GC 后堆仍持续抬升，才更像泄漏；正常缓存和一次性峰值不能直接判定为泄漏。

### P0：为什么会出现 CLS

图片、广告和异步内容要提前占位，字体策略要稳定，避免在用户正在阅读的位置插入内容：

```css
.avatar {
  width: 48px;
  aspect-ratio: 1;
  object-fit: cover;
}
```

Performance 面板中的 Layout Shift 记录能帮助定位具体节点，不要只从 CSS 猜测。

## 八、资源加载怎样做取舍

首屏关键资源优先，低频模块延后；图片明确尺寸，按场景使用现代格式、响应式图片和懒加载；脚本按路由或功能分包。`preload` 只用于当前页面很快需要的高优先级资源，`prefetch` 更偏向未来导航，不应把所有资源都加高优先级。

## 九、面试官想听到的话

### 30 秒版本

> 浏览器先把 HTML/CSS 解析为 DOM 和样式，经过样式计算、布局、绘制和合成显示。修改几何属性可能触发布局，视觉属性通常触发绘制，transform/opacity 在合适条件下可能主要走合成；读写交错还可能强制同步布局。性能我会用 Network、Performance 和真实 RUM 区分 TTFB、长任务、Layout、Paint、图片和缓存问题，再针对性优化。存储选择要看是否随请求发送、生命周期、容量、同步成本和安全边界，Cookie、localStorage、IndexedDB 不能混为一谈。

### 2 分钟版本

> 首屏和交互性能要沿完整链路分析：URL、DNS、连接、HTML/CSS/脚本、主线程执行、布局绘制到可交互。LCP 关注主要内容出现，INP 关注交互响应，CLS 关注布局跳动；它们分别对应关键资源、长任务/同步布局、尺寸预留和异步插入等问题。修改 DOM 后浏览器会批量计算，但写样式后马上读 offsetWidth 可能迫使同步布局。存储方面，服务端需要随请求的小状态可用配置过的 Cookie，少量非敏感偏好可用 localStorage，大型结构化离线数据再考虑 IndexedDB；Service Worker 能做离线策略但必须有版本和失效方案。优化前后要用相同指标验证，而不是只看 Lighthouse 分数。

## 十、自测与复习卡

1. 修改 width 和修改 color 的渲染影响有什么不同？
2. 为什么写样式后立即读 offsetWidth 可能变慢？
3. LCP、INP、CLS 各对应什么用户问题？
4. Cookie 和 localStorage 的安全与性能边界是什么？
5. 如何证明页面存在内存泄漏？
6. Service Worker 缓存为什么必须做版本治理？

```text
渲染：DOM/CSS -> Style -> Layout -> Paint -> Composite
性能：先测量 JS / 网络 / Layout / Paint / 资源
指标：LCP 主要内容，INP 交互响应，CLS 布局稳定
存储：请求携带、生命周期、容量、同步成本、安全边界
内存：看可达引用和重复操作后的 GC 后趋势
缓存：版本、过期、更新、回退、清理
```
