# HTTP/1.1 到 HTTP/3：请求为什么会排队，协议怎样减少等待

> 协议演进的主线不是“版本数字变大了”，而是浏览器页面同时需要 HTML、CSS、JS、图片和接口。怎样让这些资源更少排队、更少重复建连，并在弱网下更稳定地到达？

## 一、先从一个页面的真实问题开始

一个页面一打开，可能同时需要几十个资源。每个资源都要经历 DNS、建连、请求、响应和下载。若每个资源都重新连接，开销很大；若共用一条连接但只能一个接一个地传，又会排队。

```text
目标 1：少建连接，少握手
目标 2：多个资源能并发传输
目标 3：一个资源丢包，不要拖住所有资源
目标 4：减少重复的请求头和无效传输
```

HTTP/1.1、HTTP/2、HTTP/3 是围绕这些目标逐步演进的。理解它们前，先分清两个层次：

```text
HTTP：如何表示请求、响应、头、状态码等应用层语义
TCP / QUIC：数据怎样可靠、有序地在网络上传输
```

## 二、HTTP/1.1：先解决“每个请求都建连接”

早期 HTTP 的一个痛点是，一个资源一个连接，TCP 和 TLS 建连成本很高。HTTP/1.1 默认支持持久连接（keep-alive），同一条 TCP 连接可以连续发送多个请求：

```text
一条 TCP 连接
  请求 HTML -> 响应 HTML
  请求 CSS  -> 响应 CSS
  请求 JS   -> 响应 JS
```

这减少了重复建连，但“共用一条连接”并不等于“任意并发”。HTTP/1.1 的响应顺序受到限制；管线化虽然允许连续发多个请求，但响应仍须按顺序返回，实践中兼容性和代理问题很多，浏览器基本不把它作为解决并发的核心手段。

于是浏览器通常会对同一域名开多条连接来提高并发。这也解释了为什么过去会有域名分片、雪碧图、合并小文件等优化：它们是在 HTTP/1.1 的连接与排队约束下，尽量少发请求。

## 三、HTTP/2：把“请求”拆成可交错传输的帧

HTTP/2 没有改变 HTTP 的语义：仍然有 URL、方法、状态码和头部。它主要改变了在连接上如何传输：将报文拆成二进制帧，并给每个请求分配 stream id。

```text
一条 TCP 连接
  stream 1：HTML 的帧
  stream 3：CSS 的帧
  stream 5：JS 的帧

传输顺序可以交错：1A -> 3A -> 5A -> 1B -> 3B ...
```

这叫**多路复用**。某个大图片的应用层响应还没完成时，小 CSS 或接口响应不必在 HTTP 层排在它后面。

HTTP/2 还包括：

- **二进制分帧**：更适合协议解析与多路复用。
- **HPACK 头部压缩**：请求通常有很多重复 Cookie、Accept 等头，压缩可减少开销。
- **流优先级**：可以表达资源相对优先级，但最终效果取决于浏览器、服务器和 CDN 实现。
- **服务器推送**：曾希望主动推送可能需要的资源，但缓存匹配和资源浪费复杂，现代项目通常不应把它当主要优化手段。

### HTTP/2 仍有什么堵点

HTTP/2 的所有 stream 仍跑在同一条 TCP 连接上。TCP 为保证有序字节流，某个 TCP 包丢失时，后续字节要等待重传并按序交付。即使后续字节属于另一个 HTTP/2 stream，也可能受影响。

这叫**传输层队头阻塞**。它和 HTTP/1.1 的应用层响应排队不是同一种问题，但用户体验上同样表现为“有的资源在等”。

## 四、HTTP/3：为什么用 UDP，却仍然可靠

HTTP/3 基于 QUIC。QUIC 使用 UDP 数据报作为底座，但自己实现了连接管理、可靠传输、拥塞控制、流、多路复用和加密协商。

这里一定不要回答成“HTTP/3 换 UDP，所以不可靠”。UDP 只是底层数据报承载；**可靠性由 QUIC 协议在上层提供**。

```text
QUIC 连接
  stream 1 的某个包丢失 -> 只等待 stream 1 的缺失数据
  stream 3 的数据完整   -> 可以继续交付
  stream 5 的数据完整   -> 可以继续交付
```

QUIC 以流为单位管理数据，减少了 TCP 单一有序字节流对其他流的牵连。它还把 TLS 1.3 紧密整合进连接建立流程，并支持连接迁移：网络从 Wi-Fi 切到移动网络时，连接可以基于连接标识继续，而不必完全按旧 TCP 四元组重新开始。

“更快”仍是条件性结论。服务端/CDN 是否启用、用户网络状况、中间网络设备、资源体积和客户端支持都会影响收益。

## 五、用一个丢包场景建立直觉

假设页面同时下载 `app.js` 和一张大图，传输中大图的一部分丢包。

```text
HTTP/1.1：资源往往受连接/响应顺序限制，可能直接排队
HTTP/2：HTTP 层能交错传输，但同一 TCP 连接丢包可能影响 app.js 的后续字节
HTTP/3：图所在 stream 等待恢复，app.js 所在 stream 可在数据完整时继续
```

这正是 HTTP/3 解决的核心：不是“没有丢包”，而是“不要让一个流的丢包把其他流一起卡住”。

## 六、协议升级后，前端优化为什么仍然重要

HTTP/2 和 HTTP/3 降低了请求并发的成本，但不会替你解决：

- `app.js` 自身过大，下载和解析仍慢。
- 图片没有压缩、没有合适尺寸，字节数仍多。
- 缓存策略不当，每次都重新下载。
- 接口服务端慢，TTFB 仍高。
- JavaScript 长任务占主线程，资源到了也无法及时交互。

因此在 HTTP/2/3 环境下，过去“为了减少请求数而强行打一个巨型包”的思路不一定合适；更合理的是按缓存边界、首屏关键性和代码分割设计资源。但“文件越碎越好”也不成立，仍有请求头、调度、缓存和依赖链成本。

## 七、面试中容易混淆的点

### HTTP/2 多路复用不等于 HTTP/1.1 管线化

管线化的响应仍按顺序；HTTP/2 通过 stream 和帧真正让不同响应交错传输。

### HTTP/3 不是简单把 TCP 换成 UDP

HTTP/3 使用的是 QUIC，QUIC 在 UDP 之上重新实现可靠传输、拥塞控制和加密相关能力。

### HTTPS 不等于业务安全全部完成

HTTPS 保护传输中的机密性和完整性；登录态、权限、CSRF、XSS、输入校验仍是应用层安全责任。

## 八、面试官想听到的话

### 30 秒版本

> HTTP/1.1 用持久连接减少重复建连，但同一连接的请求响应仍有排队约束。HTTP/2 把报文拆成二进制帧，通过多个 stream 在一条 TCP 连接上多路复用，并用 HPACK 压缩头部；但 TCP 丢包会影响同连接的后续有序数据，多个 stream 仍可能被牵连。HTTP/3 基于 QUIC，虽然承载在 UDP 上，但 QUIC 自己提供可靠传输和拥塞控制，流之间的丢包影响更独立，并结合 TLS 1.3 和连接迁移改善弱网体验。协议升级后仍要做好缓存、资源体积和主线程优化。

### 2 分钟版本

> 我会从多资源并发的需求讲起。HTTP/1.1 通过 keep-alive 避免每个资源重新建 TCP 连接，但无法很好地在一条连接上让多个响应自由交错，所以浏览器曾用多连接，前端也常合并资源。HTTP/2 保留 HTTP 语义，改用二进制帧和 stream 多路复用，CSS、JS、图片的帧可以交错传输，重复头部用 HPACK 压缩。不过它仍建立在 TCP 单一有序字节流上，丢一个包会造成传输层队头阻塞。HTTP/3 的 QUIC 用 UDP 承载但在上层实现可靠性和多流控制，一个流的丢包不会像 TCP 那样拖住其他完整流。实际性能还要看 CDN、缓存、资源大小和前端执行，不能把协议升级当万能优化。

## 九、自测与复习卡

1. HTTP/1.1 的持久连接解决了什么，没解决什么？
2. HTTP/2 多路复用为什么比管线化更有效？
3. TCP 层的队头阻塞为什么会影响 HTTP/2？
4. HTTP/3 为什么“基于 UDP”仍能可靠传输？
5. 为什么 HTTP/2/3 下仍要关注包体和缓存？

```text
根问题：多资源怎样少排队、少建连、弱网更稳
HTTP/1.1：keep-alive，仍有连接/响应顺序限制
HTTP/2：二进制帧 + stream + HPACK，仍共享 TCP 的丢包影响
HTTP/3：QUIC/UDP，上层可靠传输，流间丢包更独立
工程结论：协议不是万能，缓存/体积/TTFB/主线程仍要测量
```
