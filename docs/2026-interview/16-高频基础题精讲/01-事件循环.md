# 事件循环：先把“为什么”讲明白

> 这一题不要从“宏任务、微任务”开始背。先回答一个更根本的问题：浏览器为什么需要一套事件循环机制？

## 一、这道题到底在问什么？

面试官问“说说你对事件循环的理解”，通常不是只想听你背出 `Promise` 比 `setTimeout` 先执行。他想确认四件事：

1. 你是否理解 JavaScript 在浏览器里怎样执行代码。
2. 你是否知道“等待网络、定时器、用户操作”时主线程在做什么。
3. 你能否推导异步代码的执行顺序，而不是靠记题。
4. 你能否把这个原理落到 Vue 更新、页面卡顿、请求竞态等项目问题上。

所以我们从问题开始，而不是从术语开始。

---

## 二、先补前置概念：进程、线程、调用栈

### 1. 什么是进程和线程？

可以先用一个够用的理解：

- **进程**：一个正在运行的程序及其拥有的资源空间。
- **线程**：进程内实际执行指令的一条执行路径。

浏览器是复杂程序，内部会有多个进程和线程。不同浏览器、不同版本的实现细节不完全相同，所以面试不要死说“一个 Tab 一定对应一个进程”。更准确的说法是：现代浏览器通常会把页面放在隔离的渲染进程或类似隔离环境中，以提高稳定性和安全性。

一个页面环境中，常见的工作角色包括：

```text
JavaScript 执行：运行 JS 代码
渲染相关工作：样式、布局、绘制、合成
网络 / 定时器 / 用户输入：由浏览器或操作系统能力等待和通知
```

不需要把每个网络请求都理解成“专门创建一个 JS 线程”。浏览器和操作系统如何使用 I/O、线程池或其他机制是实现细节；前端需要掌握的是：**等待网络时，JavaScript 主执行路径不必卡在那里干等。**

### 2. 为什么 JavaScript 的 DOM 操作不能随便多线程？

浏览器页面里的 JavaScript 需要读写 DOM。如果两个 JS 执行路径同时修改同一个节点，一个删除节点，一个给节点加内容，浏览器很难定义谁应该生效。

因此，浏览器中的 JavaScript 通常以单一主执行路径来执行页面脚本。它带来的好处是：同一时刻只有一段 JS 在操作页面状态，编程模型更简单；代价是：如果这条路径被长任务占住，页面就不能及时响应点击、输入和渲染。

这就是事件循环要解决的矛盾：

```text
JS 只有一条主执行路径
但页面又必须同时等待网络、定时器、用户操作和资源加载
还必须保持可以响应和渲染
```

### 3. 什么是调用栈？

调用栈就是当前正在执行的函数调用记录，遵循后进先出。

```js
function third() {
  console.log('third')
}

function second() {
  third()
  console.log('second')
}

function first() {
  second()
  console.log('first')
}

first()
```

执行过程可以理解为：

```text
first 入栈
  second 入栈
    third 入栈 -> 执行完 -> 出栈
  second 继续执行 -> 出栈
first 继续执行 -> 出栈
```

**只要调用栈没有清空，JavaScript 就不能开始执行下一段排队的回调。**

## 三、事件循环到底解决什么问题？

看下面这段代码：

```js
const result = fetch('/api/users')
console.log('继续响应用户操作')
```

如果 JavaScript 必须在 `fetch` 返回结果前停住，那么网络稍慢时，页面点击、输入、动画都会卡住。这显然无法接受。

浏览器的做法不是让 JavaScript “同时执行两个函数”，而是分工：

1. JavaScript 发起请求或注册定时器回调。
2. 浏览器相关能力在外部等待网络、时间或用户事件。
3. 条件满足后，把“可以执行的回调”放入待执行队列。
4. JavaScript 当前调用栈空闲时，事件循环再安排下一段工作进入调用栈。

```text
JS：我先登记“网络好了以后执行这个回调”
浏览器：网络由我等，JS 不要在这里阻塞
网络完成：把回调标记为可执行
事件循环：等当前 JS 任务结束，再安排这个回调执行
```

所以事件循环不是某个单独的函数，而是一套**持续协调 JS 执行、异步回调与渲染时机的调度模型**。

## 四、浏览器里到底有哪些参与者？

为了能推导执行顺序，先记住下面六个角色。它们比死记“Event Table”更接近实际工作模型。

```text
1. 调用栈：正在执行的 JS 函数
2. 任务：一段要执行的工作，例如整段 script、定时器回调、点击回调
3. 微任务队列：Promise 回调、queueMicrotask 等优先处理的回调
4. 浏览器能力：计时器、网络、DOM 事件、资源加载等
5. 渲染机会：浏览器在合适时机计算样式、布局、绘制、合成
6. 事件循环：协调“任务 -> 微任务 -> 可能渲染 -> 下一个任务”的过程
```

### 1. 任务是什么？

整段 `<script>` 可以看作一个任务。`setTimeout` 到期后的回调、用户点击回调、部分网络事件回调也会以任务形式等待调度。

注意：浏览器并不是一个简单固定数组。不同来源有不同任务源，浏览器会按规范和自身调度规则选择任务。面试里说“宏任务”可以，但更准确的术语是 **task（任务）**。

### 2. 微任务是什么？

微任务用于在当前任务结束后、进入下一次任务前尽快执行一小段后续工作。常见来源：

- `Promise.then/catch/finally` 的回调
- `queueMicrotask`
- `MutationObserver`

**重点不是“微任务更快”，而是“当前任务结束后会优先清空微任务队列”。**

### 3. 渲染什么时候发生？

浏览器通常会在任务和微任务处理之间的合适时机考虑渲染。不要回答成“每执行一个宏任务一定渲染一次”，这是不准确的。

浏览器要结合刷新率、页面是否可见、主线程是否空闲等因素安排渲染。微任务无限追加时，浏览器可能一直没有机会渲染，这就是某些页面明明在处理 Promise 却仍然卡住的原因。

## 五、最重要的工作循环

浏览器页面中，可以先用下面这个近似模型理解：

```text
取出一个任务并执行
  -> 当前调用栈清空
  -> 清空所有微任务
  -> 浏览器可能进行一次渲染
  -> 再取下一个任务
```

这里最容易漏掉两点：

1. **微任务清空时，新加入的微任务也要继续执行。**
2. **渲染是“可能发生”，不是固定发生。**

## 六、一步一步推导一段经典代码

先不要看答案，自己按“同步 -> 微任务 -> 下一个任务”推一遍。

```js
console.log('1')

setTimeout(() => {
  console.log('2')
}, 0)

Promise.resolve().then(() => {
  console.log('3')
})

console.log('4')
```

### 第一步：执行当前 script 任务的同步部分

```text
输出 1
遇到 setTimeout：登记回调，暂时不执行
遇到 Promise.then：登记微任务，暂时不执行
输出 4
当前 script 任务结束
```

此时已经输出：

```text
1
4
```

### 第二步：清空微任务

Promise 的 `then` 回调进入微任务队列，所以现在执行：

```text
输出 3
```

### 第三步：执行下一个任务

计时器到期后，它的回调作为后续任务被调度：

```text
输出 2
```

最终结果：

```text
1
4
3
2
```

### 再看一个会继续追加微任务的例子

```js
Promise.resolve().then(() => {
  console.log('A')
  queueMicrotask(() => console.log('B'))
})

setTimeout(() => console.log('C'), 0)
```

过程：

```text
当前任务结束
执行第一个微任务，输出 A，并新增微任务 B
继续清空微任务，输出 B
微任务清空后，才执行计时器任务，输出 C
```

结果是：`A -> B -> C`。

## 七、`async/await` 到底发生了什么？

```js
async function run() {
  console.log('A')
  await Promise.resolve()
  console.log('B')
}

run()
console.log('C')
```

### 按步骤解释

1. 调用 `run()`，先同步执行到 `await` 前，输出 `A`。
2. `await` 把 `run` 后半段包装成 Promise 完成后的微任务。
3. `run()` 暂时返回，主脚本继续执行，输出 `C`。
4. 主脚本任务结束，清空微任务，继续执行 `await` 后的代码，输出 `B`。

结果：

```text
A
C
B
```

**关键结论：`await` 暂停的是当前 async 函数，不是 JavaScript 主线程。**

## 八、为什么微任务太多会让页面卡住？

```js
function endless() {
  queueMicrotask(endless)
}

endless()
```

当前任务结束后，浏览器开始清空微任务。每执行一次 `endless`，它又增加一个新的微任务，于是队列永远清不空。下一次任务、渲染和用户输入都很难获得机会。

这也是为什么不要在 Promise、watcher、状态订阅中无条件地再安排同类更新。大量计算应拆分到后续任务、`requestAnimationFrame`、Worker，或直接优化算法。

## 九、事件循环和 Vue 有什么关系？

Vue 修改响应式状态后，通常不会马上更新 DOM，而是把组件更新调度到队列中合并。Vue 常利用微任务等机制尽早完成这轮更新，因此：

```js
state.count += 1
console.log(element.textContent) // 不保证已经是新 DOM

await nextTick()
console.log(element.textContent) // 可以读取这轮更新后的 DOM
```

事件循环解释了两件常见现象：

1. 同一段同步代码多次改数据，Vue 通常只更新一次视图。
2. 需要读取更新后的 DOM 时，为什么要用 `nextTick` 或 post-flush watch。

但不要简单说“Vue nextTick 就是 Promise”。Vue 会根据环境和调度策略选择实现，核心目的是管理自己的更新队列。

## 十、浏览器和 Node 不要混讲

本篇主讲浏览器。Node 也有事件循环，但它有 timers、poll、check 等阶段；`process.nextTick` 是 Node 特有的高优先级队列，不能直接等同于浏览器里的 Promise 微任务。

面试策略：

- 面试官问浏览器页面，先按“任务、微任务、渲染”回答。
- 明确问 Node 时，再讲 Node 阶段和 `process.nextTick`。
- 不确定运行环境时，先问清楚或主动说明“以下按浏览器解释”。

## 十一、常见错误回答

### 错误一：“异步任务不在主线程执行，所以 JS 多线程”

等待网络或计时器不是在 JS 调用栈中阻塞，但回调仍由 JavaScript 主执行路径执行。浏览器有并发能力，不代表你的页面 JS 回调同时并行修改 DOM。

### 错误二：“setTimeout 0ms 就是立刻执行”

0ms 只是最小延迟阈值附近的登记条件。它必须等待当前任务、微任务，以及浏览器调度。

### 错误三：“宏任务执行完一定立即渲染”

浏览器是“有机会”渲染，具体是否渲染由刷新节奏和运行状态决定。

### 错误四：“微任务比宏任务快，所以都应该用 Promise”

调度优先级不是性能优化。滥用微任务会饿死渲染和输入。

## 十二、面试官想听到的话

### 30 秒版本

> 浏览器里的 JavaScript 主执行路径是单线程的，代码通过调用栈顺序执行。但页面还要等待网络、定时器和用户操作，不能让主线程一直阻塞，所以浏览器把这些等待交给运行时能力处理，条件满足后把回调排队。事件循环会执行一个任务，清空微任务队列，再在合适时机让浏览器渲染，然后继续下一个任务。Promise 回调属于微任务，`setTimeout` 回调通常作为任务执行。这个模型能解释 Vue 的异步更新、页面长任务和请求竞态。

### 2 分钟版本

先从单线程说起：页面 JS 需要操作 DOM，如果并发修改会引入复杂同步问题，所以主执行路径一次只执行一段 JS，调用栈遵循后进先出。问题是网络、定时器、用户操作都需要等待，如果 JS 原地等待，页面就卡住了。

浏览器因此把等待工作交给网络、定时器、事件等能力处理；回调准备好后进入待调度队列。事件循环在当前任务结束后先清空微任务，再给浏览器渲染机会，然后选择下一个任务。Promise 的 `then`、`await` 后续和 `queueMicrotask` 属于微任务，计时器和用户事件通常以任务形式调度。

最后落项目：我会用这个模型解释为什么 `nextTick` 后才能读取更新后的 DOM，为什么递归 Promise 会卡住页面，以及为什么搜索请求需要取消和版本校验，不能让旧响应覆盖新状态。

## 十四、最后的复习卡

```text
先有矛盾：JS 主执行路径单线程，但页面要等待很多外部事件
解决：浏览器负责等待，回调准备好后排队，事件循环安排执行
调用栈：当前正在执行的函数
任务：一段可执行工作，例如 script、timer、click 回调
微任务：当前任务结束后优先清空，例如 Promise.then
循环：任务 -> 微任务清空 -> 可能渲染 -> 下一个任务
项目：Vue 更新、nextTick、长任务、微任务饥饿、请求竞态
```
