# 浏览器渲染流程：页面为什么会显示，又为什么会卡

> 这题不要一上来背 `DOM + CSSOM -> Render Tree -> Layout -> Paint -> Composite`。先想清楚：服务器给浏览器的是文本，屏幕需要的是像素，中间必然要有一套“理解页面、计算位置、画到屏幕”的过程。

## 一、这道题到底在问什么

面试官问“浏览器渲染流程”通常是在看你能否解释下面几类真实问题：

- 为什么改一次 `width`，可能影响许多元素的位置？
- 为什么连续读写 DOM 有时会突然很慢？
- 为什么动画通常推荐 `transform`、`opacity`？
- 为什么接口很快，首屏仍然慢？

所以这不是一道名词题。本质是：**浏览器怎样把 HTML、CSS 和 JavaScript 的结果，变成用户眼前的一帧画面；一次修改又会让其中哪些步骤重新执行。**

---

## 二、先有问题：文本不能直接变成像素

浏览器收到的 HTML 只是字符，例如：

```html
<main class="card">
  <h1>订单列表</h1>
  <button>刷新</button>
</main>
```

CSS 也只是规则：

```css
.card {
  width: 320px;
  padding: 16px;
  background: white;
}
```

要显示它，浏览器至少要回答四个问题：

```text
页面有什么节点？                 -> 结构
每个节点最后采用什么样式？         -> 外观
每个节点在什么位置、多大？         -> 几何
哪些像素该画成什么颜色、叠放顺序？ -> 画面
```

这就是渲染管线存在的原因。它不是 Vue 的流程，也不是 JavaScript 独有的流程；它是浏览器把“声明”变成“像素”的工作链。

## 三、参与者分别做什么

先把角色区分开，后面就不会混淆。

| 角色 | 它保存或负责什么 | 你可以怎样理解 |
| --- | --- | --- |
| HTML 解析器 | DOM | 页面有哪些节点、父子关系是什么 |
| CSS 解析器 | CSSOM / 样式规则 | 有哪些样式规则、选择器和继承关系 |
| 样式计算 | Computed Style | 这个节点最终真正使用哪套样式 |
| 布局 | 几何信息 | 每个盒子的大小、位置、换行结果 |
| 绘制 | 绘制记录 | 背景、文字、边框、阴影怎样画 |
| 合成器 | 图层的组合 | 把已准备好的图层组合成当前这一帧 |

这里有两个容易混淆的点：

1. **DOM 不等于屏幕上看到的东西。** `display: none` 的节点在 DOM 中存在，但不参与可见的渲染结果。
2. **CSSOM 不是简单的 CSS 文件副本。** 浏览器需要解析选择器、层叠、继承和优先级，才能计算出元素最终样式。

## 四、从 HTML 到一帧画面的主流程

先记住主链路：

```text
HTML 解析 -> DOM
CSS 解析  -> CSSOM / 样式规则
DOM + 样式规则 -> 样式计算 -> 布局（Layout）
布局结果 -> 绘制（Paint） -> 合成（Composite） -> 屏幕
```

### 1. 解析 HTML，建立 DOM

浏览器边下载边解析 HTML，逐步建立 DOM 树。遇到普通同步脚本时，脚本可能读取或修改 DOM，解析需要先停下来执行它；这也是同步脚本会影响首屏的原因之一。

```html
<script src="app.js"></script>
```

如果脚本并不依赖当前位置的解析结果，实际项目会根据场景用 `defer` 或模块脚本调整执行时机，避免无意义地挡住 HTML 解析。

### 2. 解析 CSS，计算最终样式

有了 DOM 和 CSS 规则，浏览器开始回答：每个节点最终颜色、字体、`display`、宽高规则是什么。

同一个元素可能同时匹配多条规则：

```css
button { color: black; }
.primary { color: white; }
#save { color: red; }
```

浏览器要处理来源、优先级、层叠和继承，最后得到一个元素的**计算后样式**。外部 CSS 常被称为“渲染阻塞资源”，不是因为 CSS 本身慢，而是浏览器在不知道最终样式前，不能可靠地完成页面呈现。

### 3. 布局：把“规则”变成“几何”

布局又常叫 reflow。它会计算盒模型、包含块、文字换行、Flex/Grid 分配等，产出每个可见盒子的几何信息。

```text
卡片宽度：320px
卡片左上角：(24px, 80px)
按钮宽度：96px
标题文字：在第 1 行，基线位置为 ...
```

如果父元素宽度改变，子元素可能重排，文字也可能换行；因此布局的影响范围不一定只是一处。

### 4. 绘制：生成“怎么画”的指令

绘制不是“立刻把所有像素写进显示器”，而是根据布局和样式记录该画什么：背景、圆角、边框、文字、图片、阴影等。

改 `color`、`background-color` 往往不需要重新计算几何，但需要把视觉内容重新绘制。

### 5. 合成：把图层组合成一帧

浏览器会根据实现和元素特征，将部分内容放在独立合成层或以其他方式合成。合成阶段的核心是组合已有的绘制结果，并不是“每个元素天然一层”。

`transform` 和 `opacity` 的变化在合适条件下往往可以主要停留在合成阶段，因此常适合动画；但它们不是性能免死金牌。过多图层会占用显存，也会增加管理和合成成本。

## 五、一次修改到底会触发什么

不要死记“某属性一定怎样”，要先看它改变的是几何、视觉还是合成参数。

```text
改变 width / height / margin / 字体大小
  -> 样式计算 -> 可能布局 -> 绘制 -> 合成

改变 color / background / box-shadow
  -> 样式计算 -> 绘制 -> 合成

改变 transform / opacity
  -> 样式计算 -> 在合适条件下可能主要合成
```

“可能”非常重要。元素的样式、层级、浏览器实现和上下文都会影响实际路径。面试中应说“通常会”“可能触发”，不要把优化口诀说成规范保证。

### 一个直观例子

```js
const panel = document.querySelector('.panel')

panel.style.width = '600px'       // 子元素可能需要重新布局
panel.style.background = '#fff'   // 主要改变视觉内容
panel.style.transform = 'translateX(20px)' // 常有机会主要走合成
```

第一句不仅可能改变这个面板，还可能改变兄弟元素的位置和内部文字换行。这就是“布局成本”的直觉来源。

## 六、为什么读写交错会造成强制同步布局

浏览器会尽量合并本轮 JavaScript 中的样式修改，等合适时机再统一计算和渲染。但某些读取操作必须拿到最新几何值，例如 `offsetWidth`、`getBoundingClientRect()`。

```js
box.style.width = '300px'          // 写：布局结果可能已经过期
const width = box.offsetWidth       // 读：现在就要最新宽度
box.style.width = `${width + 20}px` // 再写
```

第二行不能拿旧数据，浏览器可能被迫立刻补做样式和布局，这就是常说的“强制同步布局”。循环中不断“写 -> 读 -> 写”，成本会被放大。

更稳妥的思路是分批：先读完需要的几何信息，再集中写入。

```js
const width = box.getBoundingClientRect().width

requestAnimationFrame(() => {
  box.style.width = `${width + 20}px`
})
```

`requestAnimationFrame` 不是性能魔法，它只是把视觉更新安排到下一次绘制前的合适时机，仍然要避免在回调里做大量计算。

## 七、渲染流程和事件循环怎样配合

JavaScript 执行、微任务清空、浏览器渲染是相互协调的。一个实用近似模型是：

```text
执行一段任务
  -> 清空微任务
  -> 浏览器在合适时机考虑渲染
  -> 执行下一段任务
```

因此下面的长循环即使没有频繁改 DOM，也会卡住动画和点击响应：

```js
const end = Date.now() + 3000
while (Date.now() < end) {
  // 占住主线程
}
```

渲染并不是每个任务结束后必然发生一次；它还受刷新节奏、页面可见性和主线程是否空闲影响。正确结论是：**长任务会挤占浏览器处理输入与绘制下一帧的机会。**

## 八、遇到页面卡顿，怎样把原理落到排查

不要看到“页面卡”就直接加 `transform` 或节流。先用 Chrome Performance 等工具确认时间花在哪里：

1. JavaScript 长任务：拆分计算、减少无效循环，必要时放到 Worker。
2. Layout 很多：检查大范围几何修改、读写交错和复杂列表。
3. Paint 很重：检查大阴影、滤镜、大面积重绘和图片。
4. 首屏资源慢：检查关键 CSS、图片尺寸与格式、脚本体积和网络瀑布。
5. 列表节点多：分页、虚拟列表、减少同时挂载的内容。

性能优化的目标不是“不触发回流”，而是用测量找到真正瓶颈，并减少对关键路径和主线程的压力。

## 九、常见错误回答

### 错误一：“DOM 一变就会立刻重排重绘”

浏览器会批量处理变化；只有需要最新布局信息等场景，才可能被迫同步计算。

### 错误二：“用了 transform 就不会卡”

`transform` 通常更友好，但大图层、复杂页面、过多动画、长 JavaScript 都仍然会卡。

### 错误三：“回流一定比重绘慢，所以不要改样式”

布局通常影响更广，但性能取决于页面规模和具体修改。应该通过性能面板确认，而不是凭口诀改代码。

## 十、面试官想听到的话

### 30 秒版本

> 浏览器先解析 HTML 得到 DOM，解析 CSS 并计算每个元素最终样式，然后对可见内容做布局，得到大小和位置；接着生成背景、文字、边框等绘制结果，最后由合成阶段组合成屏幕上的一帧。几何属性变化可能触发布局、绘制和合成，颜色等视觉属性通常主要触发绘制，`transform`、`opacity` 在合适条件下可能主要走合成。实际遇到卡顿我会先用 Performance 确认是脚本、布局、绘制还是资源问题，再针对性处理。

### 2 分钟版本

> 这套流程解决的是从 HTML、CSS 文本到屏幕像素的问题。DOM 表示结构，CSS 规则经过层叠和继承计算出最终样式，布局计算每个可见盒子的几何信息，绘制生成怎么画背景、文字、阴影的记录，合成再把各部分组合成一帧。修改 `width` 会影响几何关系，所以可能触发布局；改颜色通常不改几何，主要是重绘；`transform` 和 `opacity` 常有机会主要在合成阶段更新，但不能保证。项目里我还会特别留意写样式后立即读 `offsetWidth` 这类读写交错，因为它会迫使浏览器同步计算布局。优化前先看性能时间线，不能只凭“少操作 DOM”这种泛化结论。

