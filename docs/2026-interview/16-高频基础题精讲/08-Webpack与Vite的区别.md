# Webpack 与 Vite：先分清开发体验和生产构建

> 这题最容易答成“Vite 比 Webpack 快”。这句话只有方向，没有解释。真正的差别在于：开发服务器面对一个大型模块图时，何时转换模块、浏览器如何拿模块、依赖如何处理；而生产环境仍要认真打包和优化。

## 一、先有问题：为什么大型项目启动越来越慢

假设项目有几千个业务模块和很多依赖。传统开发服务器若在浏览器打开前就要从入口开始构建完整模块图、转换并组织 bundle，首次启动自然会随着项目增长而变慢。

```text
改一个订单页
  传统预打包思路：可能要维护并更新较大的构建产物
  理想开发体验：只处理当前页面真正请求到的模块
```

Vite 的核心设计就是把浏览器已经具备的原生 ESM 能力用于开发阶段，把“尽量早构建全部”变为“浏览器请求什么，服务端就转换什么”。

## 二、Webpack 开发时的基本模型

Webpack 以模块图为中心。开发服务器通常要从入口解析依赖、应用 loader/plugin，得到可以交给浏览器执行的构建结果；修改文件后再基于依赖关系做增量更新。

```text
源码
  -> Webpack 解析/转换模块图
  -> 开发产物或内存中的 bundle
  -> 浏览器加载
```

它并不意味着每一次修改都会完整从零构建，Webpack 也有缓存、增量编译和 HMR；但大型项目的启动和更新路径仍可能受整个模块图、复杂 loader/plugin 链影响。

## 三、Vite 开发时到底怎么工作

浏览器支持 ES Module 后，可以直接请求：

```html
<script type="module" src="/src/main.ts"></script>
```

浏览器解析 `main.ts` 的 import 后，再请求它实际依赖的模块。Vite 开发服务器在请求到来时转换这个模块，并以 ESM 形式返回：

```text
浏览器请求 /src/main.ts
  -> Vite 按需转换 main.ts，返回 ESM
浏览器继续请求 App.vue、router.ts 等
  -> Vite 分别按需转换并返回
```

因此首次启动通常不需要先把所有业务源码打成一个 bundle；修改一个业务组件时，也更容易把影响范围限定在该模块及其边界附近。这就是 Vite 开发体验快的主要原因。

### 依赖预构建在解决什么

第三方依赖常是 CommonJS、UMD，或者内部有大量细碎模块。若让浏览器在开发时逐个请求与解析它们，反而会慢且兼容性差。

Vite 会对依赖进行预构建，把它们转换为更适合浏览器加载的 ESM 形式，并进行必要合并/缓存。可以把它理解为：

```text
业务源码：按请求即时转换
第三方依赖：提前整理并缓存，避免浏览器反复处理复杂依赖
```

这也是为什么首次启动或依赖变动后可能会有一次预构建；它不是 Vite “突然变慢”，而是必要的准备工作。

## 四、HMR 为什么体感快

HMR 的目标不是整页刷新，而是把变化模块替换进去，尽可能保持其他模块状态。Vite 在开发时以原生模块 URL 为边界，能更精确地推送变更；但真正速度仍受这些因素影响：

- Vue/React 等框架插件的转换成本。
- 修改是否突破 HMR 边界，是否只能回退为整页刷新。
- 大量类型检查、lint、测试是否被放在同一个 dev 进程。
- 文件系统、Monorepo 依赖解析和网络代理。

所以面试中最好说“通常更快、尤其是大型业务源码项目”，不要绝对化。

## 五、生产环境为什么仍需要打包

浏览器直接请求大量源码模块适合开发，却不等于生产最佳方案。生产仍需要：

- 删除无用代码，压缩资源。
- 处理动态 import，生成稳定的 chunk。
- 用内容 hash 做长期缓存。
- 优化 CSS、图片与资源引用。
- 兼顾目标浏览器和发布环境。

Vite 的生产构建会使用其生产构建链路（具体底层实现应以当前项目的 Vite 版本和官方文档为准），完成分包、压缩、Tree Shaking 和资源输出。稳定的面试表达是：**Vite 的优势主要来自开发服务器模型；生产仍是一场完整的构建优化工作。**

## 六、和 Webpack 的核心对照

| 维度 | Webpack | Vite |
| --- | --- | --- |
| 核心思路 | 围绕统一模块图构建与打包 | 开发利用浏览器 ESM，按需提供模块 |
| 开发启动 | 通常需要更多预先构建工作 | 业务源码多为请求时转换 |
| 三方依赖 | 纳入构建流程处理 | 预构建后缓存为适合浏览器的依赖 |
| HMR | 基于模块图的增量更新 | 以 ESM 模块边界快速更新 |
| 生产 | Webpack 产出优化资源 | 仍需完整生产构建与优化 |
| 扩展生态 | loader + plugin，历史项目成熟 | plugin 体系，部分 Rollup 生态兼容 |

表格的重点不是选边站，而是分清“开发服务”与“生产产物”这两条路径。

## 七、迁移 Vite 前，应该怎样判断

不要因“Vite 快”就重写构建。先回答四个问题：

1. 现有痛点是冷启动/HMR，还是生产包体和线上性能？
2. 是否依赖 Webpack 专属 loader、plugin、全局注入或历史资源处理？
3. 目标浏览器、内网环境、SSR、微前端、Monorepo、CI 是否有约束？
4. 环境变量、代理、别名、静态资源、测试和发布脚本能否完整迁移？

合理做法是选择低风险子应用或分支做试点，对比以下可量化指标：

```text
冷启动时间、热更新耗时、生产构建时间、产物体积、首屏关键资源、CI 稳定性、回滚成本
```

迁移后启动快了，但线上 chunk 变大、环境变量泄露或 CI 不稳定，都不能算成功。

## 八、Vue 项目中常见的迁移点

- `process.env.xxx` 通常需要迁为 Vite 的环境变量访问方式；暴露给客户端的变量应使用项目约定的前缀，例如 `VITE_`，不要把服务端秘密放进去。
- `require.context`、某些 loader 写法和 Webpack-specific plugin 不能原样搬过去，需要用 Vite/插件生态的等价方案重新设计。
- 静态资源的引用、HTML 入口、代理、别名和 SVG 处理都要逐项验证。
- 类型检查、ESLint、单测不应靠“开发服务器能跑”来证明正确，应继续保留独立质量检查。

## 九、常见错误回答

### 错误一：“Vite 不打包”

只在开发阶段尽量避免预先打全量业务 bundle；生产仍要构建优化产物。

### 错误二：“Vite 不需要处理第三方依赖”

恰恰相反，依赖预构建是它开发模型中的关键部分。

### 错误三：“Vite 一定比 Webpack 快，所以所有旧项目都该迁”

速度收益、迁移风险和生态兼容性必须一起评估。稳定、复杂的遗留项目可能更适合渐进优化现有 Webpack 配置。

## 十、面试官想听到的话

### 30 秒版本

> 两者核心差异在开发阶段。Webpack 围绕模块图进行构建，复杂项目启动和更新会受预构建与 loader/plugin 链影响；Vite 利用浏览器原生 ESM，浏览器请求哪个业务模块，开发服务器就按需转换哪个模块，并把第三方依赖预构建为适合浏览器加载的 ESM，所以冷启动和 HMR 通常更快。Vite 生产环境仍需要做分包、压缩、Tree Shaking 和 hash。迁移时我会评估现有 Webpack 扩展、浏览器兼容、环境变量、测试 CI 和可量化收益，而不是只看启动速度。

### 2 分钟版本

> 传统 Webpack 开发模型需要围绕入口维护模块图和开发构建产物，虽然有增量能力，但大型项目的启动与更新容易受全局模块图和转换链影响。Vite 在开发时直接把源码作为 ESM 提供，浏览器根据 import 逐个请求模块，Vite 按需转换；第三方依赖则先预构建，解决 CommonJS 和大量小模块的问题。因此业务代码越大，Vite 通常越能减少无关的等待。生产不是直接把源码发给浏览器，仍要构建出优化好的 chunk。实际选型还要看历史 loader/plugin、兼容性、SSR、构建脚本和团队迁移成本，我倾向先做可回滚试点，用启动、HMR、构建、包体和线上指标验证。
