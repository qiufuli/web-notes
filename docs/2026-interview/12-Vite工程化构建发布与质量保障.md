# Vite、工程化、发布与质量保障

> 工程化不是“会改配置”，而是能解释开发为什么快、生产包如何构成、问题如何定位，以及发布失败如何控制影响。

## P0：Vite 为什么开发启动快？生产构建又用什么？

### 30 秒回答

Vite 开发环境以原生 ESM 为基础，浏览器按需请求当前模块，服务端只转换被访问的代码，因此不必先打完整包。它会把依赖预构建为更适合浏览器加载的形式，常用 esbuild 提升处理速度。生产构建默认使用 Rollup 做打包、优化和分块，因此开发与生产并不是同一套工作方式。

### 展开说明

Vite 快不代表没有构建成本。首次依赖预构建、插件转换、大型依赖、类型检查和生产打包仍可能耗时。排查时先区分是 dev server 启动慢、模块热更新慢，还是 production build 慢。

### 项目表达

从 webpack 迁移时，我会先盘点 loader/plugin、环境变量、别名、静态资源、代理、HTML 模板和 CI 脚本。把旧配置逐条搬过去很危险，应确认每项配置在 Vite 下是否仍有必要或已有内置方案。

### 可能追问

- 为什么依赖需要预构建？很多依赖是 CommonJS 或包含大量小模块；预构建能转换模块格式并减少浏览器的请求与解析压力。
- Vite 完全不打包吗？开发阶段按需提供 ESM，生产阶段仍要进行 Rollup 打包优化。

## P0：如何组织 Vite 的环境变量、别名和开发代理？

### 30 秒回答

客户端可访问的环境变量需要 `VITE_` 前缀，不能把密钥放入其中，因为最终会暴露在浏览器包里。别名要与 TypeScript 路径配置保持一致。开发代理用来解决本地同源访问和转发目标，生产环境仍应由网关或服务端处理真实的跨域与鉴权。

```ts
// vite.config.ts
import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
      },
    },
  },
})
```

### 项目表达

我会为 `development`、`test`、`production` 分别维护非敏感配置，并在 CI 中显式注入环境。URL、开关和构建版本应可追溯；Token、数据库密码和第三方私钥只能留在服务端或密钥管理系统。

### 可能追问

- `.env` 能提交吗？看内容。示例文件可以提交，真实密钥不可提交；即使变量有前缀，也不能把敏感值给前端。
- alias 只改 Vite 是否够？不够，TypeScript、测试工具和 ESLint 解析通常也要识别同一别名。

## P0：前端构建和性能优化从哪里入手？

### 30 秒回答

先分析产物和用户加载路径，再优化。常见措施是路由级按需加载、拆分体积大的低频组件、移除无用依赖、选择可 Tree Shaking 的模块入口、优化图片和缓存。不要只为了降低单个 bundle 数字做过度分包，过多请求和依赖瀑布也会影响体验。

```ts
import { defineAsyncComponent } from 'vue'

const RichEditor = defineAsyncComponent(() => import('./RichEditor.vue'))
```

### 展开说明

Tree Shaking 依赖静态 ESM、正确的副作用声明和构建配置。代码分割要与路由、用户路径和缓存策略配合。优化效果应通过 bundle 分析、LCP/INP、网络瀑布图和真实监控验证。

### 项目表达

我会先确定首屏关键路径，再处理非关键编辑器、图表、导出库等大依赖。版本发布后结合 hash 静态资源的长缓存和 HTML 的短缓存，避免用户拿到新 HTML 却加载不到旧资源，或长期命中旧入口。

## P0：Source Map、错误监控与发布回滚如何协同？

### 30 秒回答

生产错误监控需要版本号、Source Map、用户上下文和请求链路信息，才能把压缩后的堆栈还原到源码。Source Map 不应无控制地公开给所有人，可上传到受控监控平台。发布采用可追溯构建、灰度或开关、指标观测和明确回滚方案，前端回滚还要考虑静态资源缓存与 API 兼容。

### 展开说明

回滚不能只把 HTML 指回旧版本：旧代码可能请求新接口，新页面也可能依赖新字段。前后端变更要优先保持向后兼容，或在发布窗口内用版本化与开关隔离。

```text
构建：注入 commit SHA 与构建时间
发布：灰度到小流量 / 指定环境
观测：错误率、关键接口失败率、LCP/INP、业务转化或核心操作成功率
回滚：恢复上一个可用构建，并确认 CDN、HTML 与接口兼容
复盘：记录触发条件、影响范围、检测延迟与改进项
```

### 项目表达

线上问题处理时，我会先止损：开关、降级、回滚或限流；再根据版本、堆栈、请求 ID 和用户操作路径定位。修复后补回归用例和监控，避免同类问题再次依赖人工发现。

### 可能追问

- Source Map 为什么可能有风险？它可能暴露源码结构、路径和注释，应控制上传与访问权限；不要把它与“代码完全保密”混为一谈。

## P1：测试体系怎么划分？

### 30 秒回答

单元测试验证纯函数和复杂分支，组件测试验证 Props、Events、状态与用户交互，端到端测试覆盖登录、权限、核心提交等关键链路。测试金字塔不是固定比例，重点是把高风险、易回归的逻辑放进稳定且运行成本合适的测试层。

### 项目表达

遗留项目不必追求一次性高覆盖率。优先为线上出过问题、改动频繁、权限和金额等高风险路径补测试，再把测试接入 CI 作为合并门禁。

## P1：如何处理前端依赖风险？

### 30 秒回答

依赖管理要关注安全公告、版本兼容、包体积、维护活跃度和许可证。升级前阅读变更说明，在独立分支或环境验证构建、核心链路和监控；不要无差别执行大版本升级，也不要长期忽略锁文件和安全告警。

## P0：Vite 中的 `import.meta.env` 和 mode 怎么理解？

### 30 秒回答

Vite 按 mode 加载对应 `.env` 文件，客户端可见变量必须有 `VITE_` 前缀；`import.meta.env.DEV/PROD/MODE` 等值会在构建时替换。它们不是运行时密钥注入方案，部署同一份静态资源到不同环境时要额外设计配置注入方式。

```ts
const apiBase = import.meta.env.VITE_API_BASE_URL
if (!apiBase) throw new Error('缺少 API 地址配置')
```

## P0：Vite 代理解决了什么，不能解决什么？

### 30 秒回答

开发代理让浏览器请求先发给本地开发服务器，再由服务器转发到后端，从而绕开本地开发时的同源限制。它不能替代生产 CORS、鉴权、TLS 或网关路由；rewrite 错误还可能导致后端收到错误路径。

## P0：为什么 Vite 项目还需要 `vue-tsc`、ESLint 和测试？

### 30 秒回答

Vite 主要负责快速转译和打包，不等于完整类型检查、代码规范和行为测试。Vue 模板类型通常由 `vue-tsc` 检查，ESLint 发现风格和部分逻辑问题，单元/组件/E2E 测试验证运行行为，CI 应把它们组合成可重复的质量门禁。

## P1：Vite 构建产物如何分析？

### 30 秒回答

先看入口 chunk、路由 chunk 和体积最大的依赖，再结合用户路径判断是否值得拆分。分析工具只能告诉你“谁大”，还要追查为什么被引入、是否可替换、是否只在低频页面使用。拆分后要看请求数量、缓存命中和 LCP 是否改善。

## P1：HMR 失效或构建变慢如何排查？

### 30 秒回答

先区分单个模块变慢、依赖预构建反复触发、插件转换耗时、文件监听过多还是机器 I/O 问题。检查配置插件、monorepo 依赖边界、软链接、环境变量和缓存目录；不要先删除所有缓存当成长期方案。

## P1：前端发布如何处理缓存和版本不一致？

### 30 秒回答

静态 chunk 使用内容 hash 和长期缓存，HTML 入口短缓存或协商缓存；发布要保证新旧 HTML 与静态资源在过渡期兼容，必要时保留旧资源。遇到 chunk load error，可提示刷新、重新加载入口或回滚版本，但不能用无限刷新掩盖部署问题。
