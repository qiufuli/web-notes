# Vite、工程化、发布与质量保障

> 工程化不是“会改配置”，而是能解释：开发为什么快、生产资源怎样构成、类型和测试如何进入门禁、线上异常怎样止损和回滚。

## 一、Vite 为什么开发阶段通常更快

大型项目冷启动慢的根本原因，是开发服务器要不要先处理完整模块图和构建产物。Vite 的开发模型利用浏览器原生 ESM：

```text
浏览器请求 main.ts
  -> Vite 按需转换并返回 ESM
浏览器继续请求 App.vue、router.ts
  -> Vite 只转换实际访问到的模块
```

第三方依赖可能是 CommonJS 或包含大量细碎模块，Vite 会先预构建为更适合浏览器加载的形式并缓存。预构建、插件转换、文件系统和 Monorepo 仍可能成为瓶颈，因此“Vite 快”是开发模型的通常优势，不是任何项目的保证。

## 二、生产构建和开发服务是两条路径

### P0：Vite 生产构建为什么仍然要打包

开发阶段按需提供 ESM 适合反馈速度；生产仍需要：

```text
Tree Shaking -> 路由/功能分块 -> 压缩 -> 内容 hash -> 资源输出
```

生产构建要结合首屏关键路径、缓存边界和浏览器支持，而不是把开发服务器的模块请求方式直接搬到线上。Vite 的具体底层构建实现要以项目版本和官方文档为准，稳定的面试表达是：**开发和生产采用不同的优化路径，生产仍是完整的构建过程。**

## 三、环境变量、别名和代理到底解决什么

### P0：客户端配置为什么不能放密钥

```ts
// vite.config.ts
import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
      },
    },
  },
})
```

客户端可见的环境变量通常要求 `VITE_` 前缀：

```ts
const apiBase = import.meta.env.VITE_API_BASE_URL
if (!apiBase) throw new Error('缺少 API 地址配置')
```

前缀只是“允许注入客户端”的开关，不是加密。Token、数据库密码、第三方私钥只能留在服务端或密钥管理系统。开发代理是本地开发服务器代替浏览器转发请求，不能代替生产 CORS、鉴权、TLS 或网关路由。

别名要同时配置 Vite、TypeScript、测试工具和 ESLint；只改一个地方会出现“编辑器能跳转但运行失败”或“构建能跑但类型找不到”。

## 四、构建性能优化应该先看用户路径

### P0：怎样从产物分析进入优化

先回答用户打开首屏实际下载什么，再决定：

```text
首屏关键：同步或优先加载
低频大模块：路由或功能懒加载
重复依赖：提取、替换或调整入口
图片/字体：尺寸、格式、压缩和缓存
```

```ts
import { defineAsyncComponent } from 'vue'

const RichEditor = defineAsyncComponent(() => import('./RichEditor.vue'))
```

Tree Shaking 依赖静态 ESM、正确副作用声明和构建配置；代码分割不是 chunk 越多越好，过多请求和依赖瀑布也会损害首屏。优化后要同时看 bundle 分析、网络瀑布、LCP/INP、缓存命中和真实监控。

## 五、缓存和版本为什么必须和发布一起考虑

一种常见策略是：

```text
带 content hash 的 JS/CSS/图片：长期缓存
HTML 入口：短缓存或协商缓存
发布过渡期：保留旧静态资源，保证新旧 HTML 兼容
```

如果新 HTML 已经发布但旧 chunk 被清理，用户可能遇到 `ChunkLoadError`；如果 HTML 长期缓存，用户又可能一直拿到旧入口。前端回滚也不只是把 HTML 指回旧版本，还要考虑 CDN、静态资源和 API 的向后兼容。

## 六、Source Map、监控和回滚怎样组成闭环

### P0：线上异常如何定位并止损

生产错误监控至少需要版本号、Source Map、用户上下文和请求链路信息：

```text
构建：注入 commit SHA / 构建时间
发布：灰度或开关控制小流量
观测：错误率、接口失败率、LCP/INP、核心业务成功率
止损：开关、降级、回滚或限流
定位：版本 + 还原后的堆栈 + request ID + 用户路径
复盘：触发条件、影响范围、检测延迟和改进项
```

Source Map 可能暴露源码结构和路径，不应无控制地公开，通常上传到受控监控平台。前后端发布要保持兼容：旧前端可能调用新接口，新前端也可能依赖新字段，必要时使用版本化或灰度开关隔离。

## 七、类型检查、Lint 和测试为什么不能只靠 Vite

Vite 主要负责快速转译和打包，不等于完整质量检查：

```text
vue-tsc / tsc --noEmit：类型与模板契约
ESLint：规范与部分逻辑问题
单元测试：纯函数、复杂分支、状态转换
组件测试：Props、Events、交互和错误态
E2E：登录、权限、提交等关键链路
```

遗留项目不必一次追求高覆盖率。优先覆盖线上出过问题、改动频繁、金额/权限/提交等高风险路径，再接入 CI 作为合并门禁。

## 八、依赖升级和 HMR 问题怎样排查

依赖管理要同时看安全公告、版本兼容、包体积、维护活跃度和许可证。升级前阅读变更说明，在独立环境验证构建、核心链路和监控，不要无差别执行大版本升级。

HMR 或构建变慢时先区分：

1. 依赖预构建反复触发。
2. 某个插件转换耗时。
3. Monorepo 软链接或文件监听范围过大。
4. 类型检查、Lint、测试被错误地串到 dev 进程。
5. 机器 I/O 或缓存目录异常。

删除所有缓存可以作为一次诊断，不是长期解决方案；应找出触发重新预构建或转换扩散的配置原因。

## 九、面试官想听到的话

### 30 秒版本

> Vite 开发阶段利用浏览器原生 ESM，业务模块按请求转换，第三方依赖预构建后缓存，因此大型项目冷启动和 HMR 通常更快；生产仍要做分包、Tree Shaking、压缩、hash 和缓存设计。环境变量中只有非敏感配置能注入客户端，别名要同步 TypeScript 和测试工具，开发代理不能代替生产鉴权。工程质量还包括 vue-tsc、Lint、单元/组件/E2E 测试，以及带版本、Source Map、监控、灰度和回滚的发布闭环。

### 2 分钟版本

> 我会先区分开发服务和生产产物。Vite 开发时浏览器按 import 请求模块，服务端按需转换；第三方依赖预构建解决 CommonJS 和细碎模块问题。生产阶段仍要围绕用户路径生成优化 chunk，首屏关键依赖优先，低频编辑器和图表懒加载，同时结合 content hash 和 HTML 缓存策略。配置上，VITE_ 前缀只表示会暴露给客户端，不能存密钥；alias、环境变量、代理要和 TS、测试、CI 一致。发布后通过 commit 版本、受控 Source Map、灰度指标和回滚策略定位与止损，且必须考虑 HTML、静态资源和 API 的兼容窗口。

```text
发布：版本、Source Map、灰度、监控、兼容、回滚
```
