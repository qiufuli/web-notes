# 网络、缓存与前端安全

> 网络题的核心是协议边界；安全题的核心是攻击面与防护组合，而不是单记一个响应头。

## P0：HTTP 缓存如何工作？

### 30 秒回答

HTTP 缓存优先看 `Cache-Control`。`max-age` 未过期时可以直接使用新鲜缓存；过期后浏览器会携带 `ETag` 或 `Last-Modified` 发起条件请求，资源未变化时服务端返回 `304`，浏览器复用本地响应体。静态带 hash 的资源可长期强缓存，HTML 通常设为短缓存或协商缓存，以便及时拿到新入口。

### 展开说明

`Cache-Control` 是现代策略的主入口。`ETag` 基于资源版本，通常比时间戳更可靠；`Last-Modified` 精度有限，也可能受文件时间变化影响。不要把“强缓存/协商缓存”理解为两个互斥开关，实际由响应指令和验证器共同控制。

```http
# 带内容 hash 的构建产物
Cache-Control: public, max-age=31536000, immutable

# HTML 入口：每次都可向服务端确认版本
Cache-Control: no-cache
ETag: "build-2026-10-09"
```

### 项目表达

发布后用户仍看到旧页面时，我会先检查 HTML 是否仍指向旧资源、CDN 是否正确刷新、静态资源 hash 是否变化、响应头是否符合策略，而不是让用户盲目清缓存。

### 可能追问

- `no-cache` 是完全不缓存吗？不是，它允许存储，但使用前必须向服务端验证。
- `no-store` 呢？要求不存储响应，常用于敏感数据；它与 `no-cache` 不同。

## P0：CORS 是什么？跨域请求到底能不能发出去？

### 30 秒回答

同源策略主要限制浏览器中的脚本读取跨源资源。跨域请求通常可以发出，但服务端如果没有给出正确的 CORS 响应头，浏览器会阻止脚本读取响应。非简单请求会先发送预检 `OPTIONS`，服务端需要明确允许方法、请求头和来源；携带 Cookie 时不能使用通配符来源。

### 展开说明

“前端不能发跨域请求”是不准确的。CORS 是浏览器执行的访问控制，服务端仍会收到很多请求；因此 CORS 也不是服务端鉴权机制。后端仍需校验身份、权限和输入。

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, X-Request-Id
```

### 项目表达

本地开发通过 Vite dev server 代理解决浏览器同源限制；生产环境通常由网关或服务端配置 CORS。代理只改变开发时的访问路径，不能替代线上跨域与鉴权设计。

### 可能追问

- 什么会触发预检？使用非简单方法、特定自定义请求头或非简单 Content-Type 等会触发，具体按 Fetch/CORS 规则判断。
- JSONP 为什么过时？它依赖 script 标签，只支持 GET，安全性和错误处理能力都有限。

## P0：Cookie、CSRF 和 XSS 应如何一起理解？

### 30 秒回答

Cookie 是浏览器按域和属性附带的状态载体。`HttpOnly` 能减少脚本直接读取 Cookie 的风险，但不能阻止浏览器自动带 Cookie，所以不能单独防 CSRF；`SameSite` 能降低跨站请求携带 Cookie 的概率，但关键写操作仍应结合 CSRF Token、Origin/Referer 校验和服务端鉴权。XSS 的根本防护是正确编码、避免不可信 HTML 和使用 CSP，而不是只依赖一个过滤函数。

### 展开说明

XSS 是攻击者让页面执行不可信脚本；CSRF 是利用用户已登录状态发起非预期请求。两者攻击路径不同，防护也不同。`v-html`、富文本展示、URL 拼接、第三方脚本是前端重点攻击面。

```http
Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'
```

### 项目表达

展示富文本时，我会明确内容来源和信任边界。来自用户或外部系统的 HTML 必须在服务端或可信库中白名单净化；能用纯文本渲染就不使用 `v-html`。涉及登录态的方案需与后端一起确认 Cookie 属性、Token 校验和跨域策略。

### 可能追问

- `HttpOnly` 能防 CSRF 吗？不能。它只限制 JavaScript 读取 Cookie，浏览器仍可能自动携带 Cookie。
- CSP 能完全消灭 XSS 吗？不能，但能显著缩小可执行脚本的范围，是纵深防御的一层。

## P1：HTTP/1.1、HTTP/2、HTTP/3 的关键差异？

### 30 秒回答

HTTP/1.1 常用持久连接，但单个连接上的响应顺序会受队头阻塞影响；HTTP/2 在一个 TCP 连接上多路复用二进制帧并支持头部压缩，但 TCP 丢包仍可能影响多个流；HTTP/3 基于 QUIC，传输层使用 UDP 并把流的可靠性隔离，减少传输层队头阻塞。HTTP/2 多路复用不是 HTTP/1.1 的管线化。

### 项目表达

协议升级不是前端性能优化的替代品。即使使用 HTTP/2/3，首屏仍会受到资源体积、优先级、主线程和服务端响应的影响。优化前先看网络瀑布图和真实指标。

## P1：`fetch` 应如何封装？

### 30 秒回答

封装应统一处理 base URL、超时或取消、状态码、业务错误、解析、请求标识和可观测性，但不应该把业务提示、页面跳转和所有错误吞到一个全局拦截器里。调用方仍要决定怎样展示当前页面的失败状态。

```js
export async function request(path, options = {}) {
  const response = await fetch(`/api${path}`, {
    credentials: 'include',
    headers: { Accept: 'application/json', ...options.headers },
    ...options,
  })

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`)
  }

  return response.json()
}
```

### 可能追问

- 如何处理超时？`fetch` 本身没有 `timeout` 选项，使用 `AbortController` 与定时器组合，并区分超时、用户取消和网络错误。
- 401 都跳登录吗？先区分未登录、Token 刷新、当前页面是否适合跳转以及是否会产生重定向循环。
