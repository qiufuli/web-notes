# 异步并发与事件循环

> 异步题的关键不是背“宏任务/微任务”名单，而是能根据规范和运行环境解释一次调度为什么发生在那个时刻。

## P0：浏览器里的事件循环是怎样工作的？

### 30 秒回答

浏览器在执行一个任务后，会清空当前微任务队列，再按需要进行渲染，然后从任务队列中取下一个任务。同步代码在当前调用栈执行；Promise 的回调和 `queueMicrotask` 属于微任务；定时器、用户交互、网络完成等回调通常以任务形式进入队列。不同来源的任务由浏览器调度，不能简单理解成一个固定的“宏任务数组”。

### 展开说明

旧资料常用 Event Table、Event Queue 来画图，这对入门有帮助，但不够准确。浏览器有多个任务源，HTML 规范定义任务与微任务检查点；渲染机会也由浏览器决定。微任务会在本轮任务结束后持续清空，因此递归安排微任务会阻塞页面响应和渲染。

```js
console.log('A')

setTimeout(() => console.log('timer'))

Promise.resolve().then(() => {
  console.log('microtask 1')
  queueMicrotask(() => console.log('microtask 2'))
})

console.log('B')

// A -> B -> microtask 1 -> microtask 2 -> timer
```

### 项目表达

我会避免在一次事件处理里堆积大量微任务或长循环。大计算拆分时，可根据优先级选择 `requestAnimationFrame`、`requestIdleCallback`（需兼容策略）或 Worker，保证输入和渲染有机会执行。

### 可能追问

- Node 的事件循环完全一样吗？不一样。Node 有自己的事件循环阶段和 `process.nextTick` 队列，不能把 Node 的输出顺序照搬到浏览器。
- `setTimeout(fn, 0)` 为什么不是立刻执行？它只表示到达最短延迟后可以排队，仍需等待当前任务、微任务及调度时机。

## P0：Promise、`async/await` 的错误传播和并发行为是什么？

### 30 秒回答

`async` 函数总是返回 Promise；`await` 会暂停当前 async 函数后续逻辑，并在 Promise 完成后以微任务继续执行。异常既可以用 `try/catch` 捕获，也会使返回的 Promise 变为 rejected。连续 `await` 会串行，彼此独立的请求应先创建 Promise，再用 `Promise.all` 并发等待。

### 展开说明

`Promise.all` 适合“全部成功才继续”的依赖；任一失败会尽快 reject，但其他请求不会自动取消。需要收集全部结果时使用 `Promise.allSettled`。`Promise.race` 是最先 settled，`Promise.any` 是最先 fulfilled。

```js
async function loadDashboard() {
  // 两个请求互不依赖，先发出，再一起等待
  const profilePromise = fetch('/api/profile').then((res) => res.json())
  const noticesPromise = fetch('/api/notices').then((res) => res.json())

  try {
    const [profile, notices] = await Promise.all([profilePromise, noticesPromise])
    return { profile, notices }
  } catch (error) {
    // 统一转换为业务可处理的错误，不吞掉错误原因
    throw new Error(`加载首页失败: ${error.message}`)
  }
}
```

### 项目表达

页面初始化时我会先画出请求依赖图。互不依赖的请求并发处理；有依赖的请求串行；部分失败可降级的区块用 `allSettled` 单独展示错误和重试入口，而不是让整个页面白屏。

### 可能追问

- `await` 会阻塞线程吗？不会阻塞浏览器线程；它只暂停当前 async 函数，其他任务仍可运行。
- Promise 回调为什么是异步的？即使 Promise 已完成，`then` 回调也会进入微任务队列，保证一致的异步语义。

## P0：如何取消请求，并避免旧请求覆盖新状态？

### 30 秒回答

浏览器中使用 `AbortController` 取消 `fetch`，组件卸载或搜索条件变化时应终止过期请求。即使无法取消后端计算，也要通过请求标识或最新值判断，避免慢响应覆盖新响应。

### 展开说明

取消不是错误处理的替代品。请求仍可能在取消前完成，因此状态更新还应与当前查询条件或序号核对。

```js
let currentController

async function search(keyword) {
  currentController?.abort()
  currentController = new AbortController()

  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`, {
      signal: currentController.signal,
    })
    return response.json()
  } catch (error) {
    if (error.name === 'AbortError') return null
    throw error
  }
}
```

### 项目表达

搜索联想、级联筛选和路由切换是最常见的竞态来源。我会同时做防抖、取消和结果版本校验：防抖降低请求量，取消减少无效工作，版本校验保证状态正确。

### 可能追问

- 防抖和节流怎么选？输入搜索通常防抖，滚动、拖拽等连续事件通常节流或基于动画帧更新。
- Axios 怎么取消？现代版本也支持 `AbortSignal`；优先使用标准 API，旧版 `CancelToken` 已不推荐。

## P1：如何实现受控并发？

### 30 秒回答

批量请求不能无上限 `Promise.all`。我会限制同时执行的任务数，任务完成后再取下一个，避免浏览器连接、服务端和客户端内存被瞬时任务压垮。

```js
async function runWithLimit(items, limit, worker) {
  const results = []
  let nextIndex = 0

  async function runWorker() {
    while (nextIndex < items.length) {
      const index = nextIndex++
      results[index] = await worker(items[index])
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, runWorker))
  return results
}
```

### 项目表达

上传多个文件、批量导出和预加载资源时，我会设置并发上限、失败重试和进度反馈。上限取值要结合接口限流、文件大小和用户网络，不是写死一个“最佳数字”。

## P1：什么时候使用 Web Worker？

### 30 秒回答

Web Worker 适合 CPU 密集、与 DOM 无关的工作，例如大数据筛选、格式转换和复杂计算。Worker 不能直接操作 DOM，与主线程通过消息通信；传输大量数据时要关注结构化克隆的成本，并可对可转移对象使用 transfer。

```js
const worker = new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })

worker.postMessage({ type: 'SORT', values: [3, 1, 2] })
worker.onmessage = (event) => {
  console.log(event.data) // [1, 2, 3]
}
```

### 可能追问

- 网络请求是否一定需要 Worker？不一定。网络 I/O 本身不会长期占用主线程，先判断瓶颈是请求、解析、渲染还是计算。

## P0：Promise 的状态、链式调用和错误传播如何理解？

### 30 秒回答

Promise 有 pending、fulfilled、rejected 三种状态，状态一旦改变就不会回退。`then` 总会返回一个新 Promise：回调返回普通值时下一个 Promise fulfilled，返回 Promise 时会跟随它，回调抛错时变为 rejected。`catch` 本质上是 rejection 分支的 `then`，所以错误可以沿链向下传播到最近的处理点。

```js
Promise.resolve(1)
  .then((value) => value + 1)
  .then(() => {
    throw new Error('failed')
  })
  .catch((error) => {
    console.log(error.message)
    return 'fallback'
  })
  .then((value) => console.log(value)) // fallback
```

### 可能追问

- `finally` 会改变结果吗？通常透传原结果；如果 finally 回调抛错或返回 rejected Promise，会覆盖原结果。
- 为什么只写 `try/catch` 抓不到未 await 的 Promise？没有等待或返回的异步链不在当前 try 的同步控制范围内。

## P0：`Promise.all` 失败后，其他任务会怎样？

### 30 秒回答

`Promise.all` 在任一输入 rejected 后会尽快 reject，但不会自动取消其他已经开始的任务。需要真正停止网络请求时，必须把同一个 `AbortSignal` 传给各任务；需要收集所有结果时使用 `Promise.allSettled`。选择组合器时要先说清楚业务是 fail-fast 还是允许部分成功。

```js
async function loadCards(signal) {
  const tasks = ['/a', '/b', '/c'].map((path) =>
    fetch(path, { signal }).then((res) => res.json()),
  )
  return Promise.all(tasks)
}

const controller = new AbortController()
loadCards(controller.signal).catch((error) => {
  if (error.name !== 'AbortError') console.error(error)
})
controller.abort()
```

## P0：微任务为什么可能让页面“卡住”？

### 30 秒回答

浏览器通常会在当前任务结束后清空微任务队列，只有微任务清空后才可能进入渲染。如果微任务不断给自己追加新的微任务，就会长时间占用主线程，让绘制、输入和定时器都得不到机会。大量连续工作应拆成任务或交给 Worker。

```js
let count = 0
function loop() {
  if (count++ < 100000) queueMicrotask(loop)
}
loop()
```

### 项目表达

状态批量更新可以利用微任务，但不要在 watcher、Promise 回调或状态订阅中无条件再次触发同类更新。遇到输入延迟，我会检查长任务和微任务链，而不只盯着网络耗时。

## P1：`requestAnimationFrame`、`setTimeout` 和 `requestIdleCallback` 怎么选择？

### 30 秒回答

动画或每帧视觉更新用 `requestAnimationFrame`，它与浏览器绘制节奏对齐；普通延迟任务用 `setTimeout`，但延迟只是最早执行时间；低优先级非关键工作可尝试 `requestIdleCallback`，但必须有超时和降级，因为空闲时间不保证出现。

```js
let pending = false
window.addEventListener('scroll', () => {
  if (pending) return
  pending = true
  requestAnimationFrame(() => {
    pending = false
    updatePosition()
  })
})
```

## P1：如何设计重试、超时和取消？

### 30 秒回答

超时、取消、重试是三种不同状态：超时是客户端主动放弃，取消可能来自用户或组件卸载，重试是对暂时失败的再次尝试。只对幂等或具备幂等键的操作重试，并使用指数退避和次数上限；错误信息要保留原始原因。

### 项目表达

列表查询可以对网络抖动做有限重试，支付、创建订单等写操作不能仅靠前端重试。请求封装应让调用方区分取消与失败，避免把用户主动离开页面记录成系统错误。
