# 异步并发与事件循环

> 异步题不要只背“宏任务/微任务”。先说明矛盾：JavaScript 主执行路径要保持可预测，但页面又要等待网络、定时器、用户输入和渲染；然后再解释 Promise、取消和并发控制如何配合。

## 一、浏览器异步到底解决什么问题

JavaScript 执行代码时通常只有一条主执行路径。如果它同步等待网络：

```js
const data = waitForNetwork() // 假设这里阻塞 3 秒
render(data)
```

那么点击、输入和绘制都会被堵住。浏览器的做法是让网络、定时器和输入等待由运行时能力处理，条件满足后把可执行回调交给 JavaScript；JavaScript 本身仍然一次执行一段任务。

```text
当前任务执行
  -> 当前调用栈清空
  -> 清空微任务
  -> 浏览器在合适时机考虑渲染
  -> 取下一个任务
```

这里的“任务”来自多个来源，不是一个固定的 Event Table。浏览器具体如何调度不同任务源，也不能简单画成一个宏任务数组。

## 二、Promise 和 async/await：异步结果怎样组合

### P0：Promise 的状态和错误传播

Promise 有 pending、fulfilled、rejected 三种状态，落定后不可回退。`then` 一定返回新 Promise：返回值会成为下一环节的结果，返回另一个 Promise 时会跟随它，抛错则进入 rejected。

```js
Promise.resolve(1)
  .then((value) => value + 1)
  .then(() => { throw new Error('failed') })
  .catch(() => 'fallback')
  .then((value) => console.log(value)) // fallback
```

`catch` 是 rejection 分支的 `then`；`finally` 通常透传原结果，但如果自身抛错或返回 rejected Promise，也会改变最终结果。没有 `await` 或 `return` 的 Promise 不在当前 `try/catch` 的控制链内。

### P0：`async/await` 为什么看起来像同步

```js
async function loadUser() {
  const response = await fetch('/api/user')
  return response.json()
}
```

`async` 函数总返回 Promise；`await` 暂停的是当前 async 函数的后半段，不是浏览器主线程。Promise 完成后，后半段作为微任务继续执行。连续 `await` 会串行，独立请求要先启动再等待：

```js
const profilePromise = fetch('/api/profile').then((res) => res.json())
const noticesPromise = fetch('/api/notices').then((res) => res.json())

const [profile, notices] = await Promise.all([profilePromise, noticesPromise])
```

`Promise.all` 适合全部成功才继续，`allSettled` 适合允许部分失败；`race` 取最先落定，`any` 取最先成功。

## 三、经典执行顺序怎样推导

```js
console.log('A')

setTimeout(() => console.log('timer'), 0)

Promise.resolve().then(() => {
  console.log('microtask 1')
  queueMicrotask(() => console.log('microtask 2'))
})

console.log('B')
```

按因果关系推导：

1. 当前 script 任务先同步输出 `A`。
2. `setTimeout` 注册一个未来任务，当前不执行。
3. `then` 注册微任务，当前不执行。
4. 同步代码输出 `B`，script 任务结束。
5. 清空微任务，输出 `microtask 1`，并追加 `microtask 2`。
6. 继续清空微任务，输出 `microtask 2`。
7. 后续某个任务时机执行 timer。

结果是：

```text
A -> B -> microtask 1 -> microtask 2 -> timer
```

`setTimeout(fn, 0)` 只是允许回调最早在延迟阈值后排队，仍要等待当前任务和微任务，也不保证精确 0ms 执行。

## 四、取消和竞态：为什么“请求发出去了”还不够

### P0：如何取消请求，避免旧响应覆盖新状态

搜索输入快速变化时，旧请求可能比新请求更晚返回。如果旧结果直接写状态，就会显示错误关键词的数据。要同时处理防抖、取消和版本校验：

```js
let controller
let version = 0

async function search(keyword) {
  controller?.abort()
  controller = new AbortController()
  const currentVersion = ++version

  try {
    const response = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`, {
      signal: controller.signal,
    })
    const data = await response.json()
    if (currentVersion === version) render(data)
  } catch (error) {
    if (error.name !== 'AbortError') throw error
  }
}
```

取消减少无效网络和解析工作，但不保证后端已经停止计算；版本校验负责保证状态正确。组件卸载、路由离开和筛选条件变化都是取消旧请求的时机。

## 五、受控并发：为什么不能无限 Promise.all

批量上传、导出或预加载如果一次性启动几百个任务，会占用连接、内存和服务端并发额度。可以限制同时执行数量：

```js
async function runWithLimit(items, limit, worker) {
  const results = []
  let nextIndex = 0

  async function runWorker() {
    while (nextIndex < items.length) {
      const index = nextIndex++
      results[index] = await worker(items[index])
    }
  }

  await Promise.all(
    Array.from({ length: Math.min(limit, items.length) }, runWorker),
  )
  return results
}
```

上限不是固定最佳值，要结合接口限流、用户网络、文件大小和失败重试。重试也不是取消的替代品：只对幂等或有幂等键的操作有限重试，并使用指数退避和上限。

## 六、微任务、动画和 Worker

微任务会在当前任务后持续清空；如果微任务不断追加自己，渲染和输入可能一直没有机会：

```js
function loop() {
  queueMicrotask(loop)
}
// loop() // 不要在页面中这样运行
```

动画或每帧视觉更新适合 `requestAnimationFrame`；普通延迟用 `setTimeout`；低优先级任务可尝试 `requestIdleCallback`，但要有超时和降级。CPU 密集且不需要 DOM 的计算可放 Web Worker，网络 I/O 本身不一定需要 Worker。

```js
const worker = new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })
worker.postMessage({ type: 'SORT', values: [3, 1, 2] })
worker.onmessage = (event) => console.log(event.data)
```

## 七、面试官想听到的话

### 30 秒版本

> 浏览器把网络、定时器和输入等待交给运行时能力，JavaScript 主执行路径一次执行一个任务；任务结束后清空微任务，浏览器在合适时机渲染，再处理后续任务。Promise 回调和 await 后半段属于微任务，setTimeout 通常以任务执行。Promise 组合时，独立请求要并发，全部成功用 all，允许部分失败用 allSettled。搜索和路由切换要处理取消与旧响应竞态，批量任务要限制并发。Node 有自己的事件循环阶段，不能和浏览器调度完全混答。

### 2 分钟版本

> 事件循环解决的是“主执行路径要可预测，但页面又需要等待外部事件”的矛盾。当前任务执行完后，浏览器清空微任务，微任务中新追加的微任务也会继续执行，之后才可能安排渲染和下一个任务。经典顺序题先执行同步代码，再执行 Promise.then 和 queueMicrotask，最后才是定时器。异步业务中我会先画请求依赖图，独立请求并发，有依赖再串行；对搜索、路由和组件卸载使用 AbortController，并用版本号防止旧响应覆盖新状态；批量上传等场景限制并发，重试只用于幂等操作。性能问题还要警惕无限微任务和长任务阻塞输入与绘制。

```text

```
